# 資料取得方針 v3（確定版）

## 0. 方針

**本部（運営会社）が、自社の全省庁統一資格とICカードを使って、必ず資料を取得する。**

理由は明快です。**資料を取得しないと案件の内容が分からず、AI解析も、提案も、必要業種の判断も、
見積依頼も一切できません。** 公告の表題だけでは何も判断できないため、ここは事業の前提条件です。

そのうえで、**顧客は顧客ごとに、自分の名義で資料を取り寄せます。** 本部の取得はこれに代わりません。

**顧客の委任による代行取得は行いません。**（一度検討しましたが、取り下げます。
顧客ごとに正式取得が必要である以上、代行しても手続きが二重になるだけで、責任の所在も曖昧になります）

## 0-1. 実機で確認した結果（2026/08/01・重要）

調達ポータルの画面を実際に操作して確認しました。**ICカードは資料取得に不要でした。**

### 確認した経路

```
調達情報の検索（ログイン不要）
  └ 検索結果一覧 → 公示本文 → 調達情報の詳細
       └ 「調達資料 ダウンロードURL」
            └ 連絡先情報入力方法選択
                 ├ 電子調達システムに登録している連絡先情報を利用する → ICカードログインが必要
```

**ICカードもログインも不要で、資料一式が取得できました。**

| 項目 | 変更前 | **変更後** |
|---|---|---|
| ICカード収集端末 | 全案件の資料取得に必要 | **原則不要。**例外的にICカードでしか取れない案件があれば、そのときだけ使う |

| 契約書関連 | その他 |

### 必ず認識しておくこと

**連絡先情報として東北三上機材株式会社の名義が記録されます。**
これは「当社が自社名義で資料を取得している」ということであり、方針どおりです。
ただし次の3点を守ってください。

1. **顧客の名義では取得しない**（委任代行は行わない方針のまま）
2. **顧客に原本を配らない**（解析結果と引用のみ提供）
3. **参加意思のない案件を無制限に取得しない**（顧客の条件に該当しうる案件に限定する）

※ 添付に「電子調達システムによる入札説明書等資料交付について」というPDFが含まれています。
**交付を受けた者の扱いについて記載がある可能性が高いので、必ず中身を確認してください。**
参加条件に「入札説明書の交付を受けた者に限る」とある案件では、この記録の名義が問題になります。

## 0-2. 取得する資料と、提案の判断

### 取得は5種類すべてを試みる

| 種別 | AI解析 | この資料から取るもの |
|---|---|---|
| 公告 | ○ | 案件名・機関・期限（提出／質問／開札）・資格区分・等級・地域・予定価格 |
| 入札説明書 | ○ | 参加条件・提出書類・手続き・正式取得の方法 |
| 仕様書 | ○ | **必要な協力業種と根拠**・履行条件・制約表現 |
| 数量表 | ○ | 行ごとの項目・仕様・数量 → **業種の割当** |
| 様式 | ○ | 提出書類の一覧 |

**取得した資料はすべてAI解析にかけます。** 公告だけを解析対象にする設計にはしません。

### ただし、揃わないことを理由に提案を止めない

**案件によっては、そもそも入札説明書と仕様書しか存在しません。**（数量表がない役務案件は普通にあります）
「5種類揃わないから提案しない」は誤りです。

**提案の可否は「資料が揃ったか」ではなく「提案できる内容が揃ったか」で判断します。**

| | 条件 |
|---|---|
| **提案する** | 案件名・発注機関・提出期限・資格区分／等級／地域 が確定している |
| 提案しない | 上記が確定できない（＝参加可否すら判断できない） |

判定できない項目は、**推測せず「未判定」と明示したうえで提案します。**

```
例：仕様書が取得できていない案件
  → 提案は出す
  → 適合率は算出できる範囲で出し、協力会社の項目は「未判定」
  → 画面に「仕様書が未取得のため、必要な協力業種は判定できていません」と表示
  → 見積依頼のステップに進むときに、取得を促す
```

**黙って欠けた状態で提案するのが最悪です。** 何が分かっていて何が分かっていないかを明示すれば、
ユーザーは自分で判断できます。

### 資料が無い理由を2つに分ける

これを混同すると、失敗アラートがノイズだらけになります。

| 区分 | 例 | 扱い |
|---|---|---|
| **機関が出していない**（正常） | 数量表が存在しない役務案件 | `not_published`。アラートしない。UIは「この案件には数量表がありません」 |
| **取得に失敗した**（要対応） | ICカードが必要、リンク切れ、OCR失敗 | `failure_code` を記録。手動取得の対象。UIは「取得できていません」 |

**この2つは画面上も文言を変えてください。** 「ありません」と「取れていません」は意味が違います。

## 1. 2つの取得を、はっきり分ける

| | ① 本部の取得 | ② 顧客の正式取得 |
|---|---|---|
| 誰が | 運営会社（自社の資格・ICカード） | 顧客自身 |
| 何のために | **AI解析・提案・見積依頼のため** | **入札に参加するため** |
| いつ | 案件を検知したら毎回（自動） | 顧客が参加を決めたとき |
| 対象 | 全案件 | 参加する案件のみ |
| 資料の扱い | **顧客には原本を渡さない**（解析結果・引用・公告元URLのみ） | 顧客の手元に残る |
| システム上 | `tenders.collect_status` | `company_tenders.official_status` |

**この2つを混同させないことが、UI設計の最重要事項です。**
顧客が「システムが持っているなら自分は取らなくていい」と誤解すると、失格に直結します。

## 2. ICカードが必要な取得を、どう自動化するか

電子調達システムでの資料取得にはICカードとPINが必要です。
**ICカードは物理カード＋カードリーダー＋PINなので、クラウドのサーバーからは操作できません。**
カード内の秘密鍵は取り出せない設計になっているため、リモート化もできません。

### 構成：収集端末を1台立てる

```
┌─ クラウド ───────────────────────────────┐
│ Vercel（画面）                            │
│ Supabase（DB・Storage）                   │
│ Railway ワーカー                          │
│   ├ 公開範囲の巡回・新規案件の検知        │
│   ├ 公開PDFの取得                         │
│   └ AI解析・提案・通知                    │
└──────────────┬───────────────────────────┘
               │ ジョブ（pg-boss）
               ▼
┌─ 社内の収集端末（Windows・常時起動） ────┐
│ ICカードリーダー ＋ ICカード              │
│ 常駐エージェント（Node + Playwright）     │
│   ├ ジョブを取りに行く                    │
│   ├ 電子調達システムにログイン            │
│   ├ 資料をダウンロード                    │
│   └ Supabase Storage へアップロード       │
└──────────────────────────────────────────┘
```

**クラウド側は資料取得以外のすべてを担当し、ICカードが要る部分だけを社内端末に降ろします。**
端末はDBに対してジョブを取りに行くだけなので、外部から社内への通信は開けません（ポート開放不要）。

### 端末の要件

| 項目 | 内容 |
|---|---|
| OS | Windows（電子調達システムの推奨環境に合わせる） |
| 機器 | ICカードリーダー、ICカード（電子証明書） |
| 電源・回線 | 常時起動・有線推奨。UPSがあると安心 |
| 稼働 | 毎日 04:00 と 12:00 にジョブを処理 |
| 監視 | 30分ごとにDBへ死活を書き込む。**60分書き込みがなければアラート** |

## 3. 運用上のリスクと対策（ここが事業の急所）

| リスク | 影響 | 対策 |
|---|---|---|
| **PINを数回間違えてカードがロック** | **収集が全停止** | PINは端末の資格情報として保管し、リトライは**1回まで**。失敗したら即停止して人へ通知。自動リトライを絶対に入れない |
| **カードが1枚しかない** | 単一障害点。故障・紛失で全停止 | **2枚目を取得して予備にする**（同一法人で複数枚を持てます）。年1回、予備での動作確認 |
| **電子証明書の有効期限切れ** | ある日突然すべて止まる | 有効期限をDBに登録し、**90日前・30日前・7日前にアラート** |
| 同時実行できない | 取得が詰まる | ジョブは直列。1件あたりの所要時間を計測し、日次で捌ける件数を把握しておく |
| 端末の故障・停電 | 収集停止 | 予備端末の手順書を用意。**復旧手順を文書化**（譲渡時にも必要） |
| 電子調達システムの仕様変更 | セレクタが空振り | `LAYOUT_CHANGED` で即アラート。ステージングで並走 |

**PINの自動リトライだけは、絶対に入れないでください。** ロックすると再発行に日数がかかり、その間サービスが止まります。

## 4. 取得件数を抑える設計（重要）

本部の資格で全案件の資料を取得すると、**参加意思のない案件の資料を大量に取得する形**になります。
発注機関側から見て不自然に映らないよう、以下を設計に入れます。

1. **取得するのは、いずれかの顧客の条件に該当しうる案件だけ**にする
   （営業品目・地域で明らかに対象外の案件は、公告の表題と基本情報だけを保存し、資料は取得しない）
2. 1案件につき1回。**同じ資料を再取得しない**（sha256で判定）
3. アクセス間隔をあける。短時間の連続取得をしない
4. 取得件数を日次で記録し、**急増したら通知**する

これは技術ではなく礼儀の問題ですが、ブロックされると事業が止まるので、実装で担保します。

## 5. 顧客側の正式取得を、どう案内するか

本部が資料を持っていても、**顧客は自分で取り寄せる必要があります。** ここを丁寧に設計します。

- 進め方のステップ3は「資料を正式に取得する」のまま。**人がやる4つの作業の1つ**
- 案件ごとに、取得方法（電子調達システム／メール交付／FAX）と手順を表示
- 顧客の取得状況を `未取得 → 申請中 → 取得済` で管理し、**取得済みになるまで提出書類の作業を促さない**
- 資料タブには常に次の一文を表示する

> システムが取得した資料は、AIが解析するためのものです。
> 入札に参加するには、御社の名義で入札説明書等を取得してください。

## 6. 法務で確認すること（弁護士確認の1番目）

**自社の入札参加資格とICカードで取得した資料を、他社向けの有料サービスの解析に利用すること**の整理。

- 電子調達システムの利用条件に抵触しないか
- 取得した資料の原本を顧客に配布しない方針で足りるか
- 解析結果（要約・引用・必要業種の判断）を提供することの可否
- 自社が参加しない案件の資料を継続的に取得することの是非

**原本を配らない、という方針はこの変更後も維持します。** ここが崩れると再配布の問題が正面から出ます。

## 7. 実装への反映

### データモデル（追加）

```sql
-- 収集端末（ICカード稼働機）の死活と証明書の期限
create table collector_agents (
  id            text primary key,           -- 'agent-01'
  label         text not null,
  cert_expires_on date,                     -- 電子証明書の有効期限
  last_heartbeat_at timestamptz,
  status        text not null default 'idle', -- idle/running/error/locked
  detail        jsonb
);

-- 取得の記録（本部）
alter table tender_documents add column acquired_via text;  -- public / geps_ic
alter table tender_documents add column agent_id text references collector_agents(id);
```

### ジョブの分岐

```
crawl（クラウド）
  └ 新規案件を検知
       ├ 公開範囲で取得できる資料 → クラウドで取得
       └ ICカードが必要な資料 → job: fetch_documents_ic をキューに積む
                                   └ 収集端末が処理
```

### エラーコードの追加

| コード | 意味 | 対応 |
|---|---|---|
| `IC_CARD_LOCKED` | PINロック | **即アラート。自動リトライしない** |
| `IC_CARD_ABSENT` | カード未挿入・リーダー未認識 | 即アラート |
| `CERT_EXPIRED` | 証明書の期限切れ | 即アラート |
| `AGENT_DOWN` | 端末からの死活が60分途絶 | 即アラート |

### 監視に追加

- 収集端末の死活（60分）
- 電子証明書の残日数（90/30/7日）
- 日次の取得件数（急増・ゼロの両方を検知）
