# AI入札部 実装仕様書 v1（8月β着手用）

対象：全省庁統一資格で参加できる案件（物品・役務）。自治体・工事は将来拡張。
この文書だけで実装に着手できることを目標にしている。プロトタイプ（v3）は本仕様のUI側の見本。

---

## 0. 設計の前提

1. **案件は全ユーザー共通で1レコード**。企業ごとのデータ（提案・正式取得・対応・見積）は必ず別テーブル。
2. **本部が必ず資料を取得する**（→ `資料取得方針_v3.md`）。資料がないと解析も提案も見積依頼もできないため、これは前提条件。
   - 電子調達システムの資料取得にはICカードとPINが必要 → **社内の収集端末（カードリーダー付き）で実行**し、クラウドからジョブを渡す
   - 取得した原本は顧客に配らない（解析結果・引用・公告元URLのみ提供）
   - **顧客は顧客ごとに自分の名義で正式取得する。** 本部の取得はこれに代わらない。委任による代行取得は行わない
3. **AIの出力には必ず根拠を持たせる**。どの資料の何章から抽出したかを保存しないと、誤りを検証できずクレームに耐えられない。
4. **失敗は握りつぶさない**。取得失敗・解析失敗は理由付きでキューに残し、人が処理できる導線を必ず用意する。

---

## 1. モジュールと依存

```
connectors/   取得元ごとの実装（listNew / fetchDocuments / healthCheck）
              ※ 案件の発見は KKJ API を第1層とする（→ 案件収集戦略_v2.md）
crawler/      スケジュール実行・新規検知・リトライ・失敗記録
documents/    資料の保管（S3）・種別判定・ハッシュ・重複排除
parser/       OCR + LLM で構造化。tender_analyses へ書き戻す
db/           案件マスタ（全ユーザー共通）
proposal/     条件セットとの照合・適合率・理由生成
notification/ 配信（アプリ内・メール・LINE）
quotes/       見積依頼・回収・返信パース・比較
costing/      原価集計・応札価格の検討
forms/        提出書類の抽出とチェック
awards/       落札結果と相場
```

依存は一方向：`connectors → crawler → documents → parser → db ← proposal → notification`
`parser` と `proposal` は純関数（入出力JSON）として実装し、単体テスト可能にする。

## 3. コネクタ

```ts
export type DocKind = "公告" | "入札説明書" | "仕様書" | "数量表" | "様式" | "その他";

export interface TenderSeed {
  agencyId: string;
  noticeNo?: string;
  name: string;
  procurement: "役務" | "物品" | "工事";
  qualCategory: string;
  item?: string;
  grade?: string;
  areas: string[];
  submitDeadline?: string;   // ISO
  qaDeadline?: string;
  bidOpenAt?: string;
  budget?: number | null;
  sourceUrl: string;
  acquireMethod: string;
  documentLinks: { kind: DocKind; url: string }[];
}

export interface TenderConnector {
  id: string;
  kinds: ("役務" | "物品" | "工事")[];
  /** 一覧から新規を拾う。since 以降の掲載分のみ。 */
  listNew(since: Date): Promise<TenderSeed[]>;
  /** 資料を取得。公開範囲で取れないものは reason つきで skipped に入れる。 */
  fetchDocuments(seed: TenderSeed): Promise<{
    fetched: { kind: DocKind; buffer: Buffer; url: string }[];
    skipped: { kind: DocKind; code: string; reason: string }[];
  }>;
  healthCheck(): Promise<{ ok: boolean; detail?: string }>;
}
```

**追加手順（機関を増やすとき）**
1. `agencies` にレコードを追加（掲載URLと期待更新頻度）
2. 既存コネクタで取れるなら設定追加のみ。取れないなら新規コネクタを1つ書く
3. ステージングで7日間並走させ、欠測アラートが出ないことを確認してから本番へ

**重複排除**：`dedupe_key = agency_id + "/" + notice_no + "/" + date(submit_deadline)`
`notice_no` が無い機関は `agency_id + "/" + sha1(normalize(name)) + "/" + date(submit_deadline)`。
normalize は空白・全半角・括弧・年度表記を統一する。

## 4. AI解析（parser）

### 4.0 解析対象（5種類すべて）

**公告・入札説明書・仕様書・数量表・様式のすべてをAI解析にかけます。** 公告だけではありません。

| 資料 | 主に抽出するもの |
|---|---|
| 公告 | 案件名・機関・期限（提出／質問／開札）・資格区分・等級・地域・予定価格 |
| 入札説明書 | 参加条件・提出書類・手続き・正式取得の方法・質問の方法 |
| **仕様書** | **必要な協力業種と根拠**・履行条件・制約表現（「〜に限る」「〜は落札者負担」） |
| **数量表** | 行ごとの項目・仕様・数量・単位 → **業種の割当** |
| **様式** | 提出書類の一覧（様式番号・名称・必須か） |

**資料は5種類すべてを取得しにいきますが、揃わないことを理由に提案を止めません。**
提案の可否は「案件名・発注機関・提出期限・資格区分／等級／地域が確定しているか」で判断します。
判定できない項目は推測せず `null` とし、UIに「未判定」と表示します（→ `資料取得方針_v3.md`）。

資料が無い理由は `not_published`（機関が出していない・正常）と `failure_code`（取得失敗・要対応）に分けて記録します。

### 4.1 前処理
- テキストPDF：そのまま抽出。画像PDF：OCR。表領域は表構造のまま抽出し、数量表はCSVへ正規化
- 資料はすべて連結せず、**資料種別ごとに分けてモデルへ渡す**（出典を特定できなくなるため）
- KKJ APIで得られる公告本文は**補助入力**として使ってよいが、資料の代替にはしない

### 4.2 出力スキーマ（tender_analysis v1）

```json
{
  "summary": "string (200字以内)",
  "qualifications": [{ "text": "string", "source": "資料種別 + 章番号" }],
  "conditions":     [{ "text": "string", "source": "string" }],
  "trades": [{
    "trade": "清掃|警備|設備保守|…",
    "confidence": 0.0,
    "evidence": "引用元の短い記述",
    "excluded": false,
    "excluded_reason": "別契約のため 等"
  }],
  "lots": [{ "line_no": 1, "item": "string", "spec": "string",
             "qty": 0, "unit": "string", "trade": "string", "confidence": 0.0 }],
  "estimate_scope": ["string"],
  "forms": [{ "name": "string", "source": "様式第1号", "required": true, "note": "string" }],
  "notes": [{ "text": "string", "source": "string" }],
  "official_acquire": "string",
  "deadlines": { "submit": "ISO|null", "qa": "ISO|null", "bid_open": "ISO|null" },
  "unknown_fields": ["budget", "..."]
}
```

**規則**
- 分からない項目は推測せず `null` にし、`unknown_fields` に列挙する
- `evidence` は必須。原文からの短い引用（30字以内）＋出典。ここが空の項目はUIで「未確認」として扱う
- 期限は必ず日時に正規化。年度表記（令和8年度）は西暦に変換
- `confidence < 0.30` の業種は `excluded: true` にして依頼対象から外す（しきい値は設定で変更可能に）

### 4.3 プロンプト

**本文は `AI解析プロンプト集.md` を正とします。** 以下は骨子です。



システム：
> あなたは公共調達の入札公告を読む担当者です。与えられた資料から指定のJSONだけを出力します。資料に書かれていないことは推測せず null にします。すべての抽出項目に、原文の短い引用と出典（資料種別と章番号）を付けます。

ユーザー：資料種別・本文・既知のメタ情報（機関名・公告番号）＋出力スキーマ。

**別プロンプトに分ける処理**（1回で全部やらせない。精度が落ちる）
1. 基本情報と期限の抽出
2. 参加資格・参加条件の抽出
3. 数量表の構造化と業種割当
4. 提出書類（様式）の抽出
5. 注意事項の抽出（「〜に限る」「〜は落札者負担」など制約表現を優先）
6. 質問案の生成（矛盾・数量の欠落・範囲が不明瞭な箇所を最大3件）

### 4.4 返信パース（見積の自動取込）
- 入力：メール本文/LINEテキスト＋添付（PDF/Excelは金額欄を抽出）
- 出力：`{ amount: number|null, currency: "JPY", tax_included: bool|null, declined: bool, needs_survey: bool, note: string }`
- **金額が1つに定まらない場合は null**。複数金額（内訳）がある場合は合計を推定せず、人の確認へ回す
- 取り込み時は必ず「元の文面」を並べて表示する（誤取込の発見を早くする）

### 4.5 精度の測り方
- ゴールドセット：実案件20件を人手で正解付け（期限・資格・必要業種・提出書類）
- 合格ライン：期限100%、参加資格95%、必要業種のF1 0.85、提出書類の再現率0.95
- リリース前と、プロンプト・モデル変更のたびに実行する

## 5. ジョブ設計

| ジョブ | 頻度 | 冪等キー | 備考 |
|---|---|---|---|
| **kkj_sync** | 04:00 / 12:00 | date + 区分 | **案件の発見。官公需情報ポータルAPI（→ 案件収集戦略_v2.md）** |
| crawl | 04:00 / 12:00 | connector + date | 調達ポータル等の巡回（当日ぶんの補完）。同一ドメインは1並列・1req/2秒 |
| fetch_documents | crawlから起動 | tender + kind + sha256 | 匿名取得を試す。同一ハッシュは再取得しない |
| **fetch_documents_ic** | 上記が認証を要求したとき | tender + kind | **収集端末（ICカード機）が処理**（→ 資料取得方針_v3.md）。PINの自動リトライ禁止 |
| **import_awards** | 月次 | データセット版 | 落札実績オープンデータの取り込み |
| parse | 資料取得完了時 | tender + version | 失敗は3回まで指数バックオフ |
| match（提案） | parse完了時 + 条件セット更新時 | org + tender + criteria_set | `検討中` 以降のproposalは上書きしない |
| notify | match直後 | proposal | 1日1通にまとめる（案件ごとに送らない） |
| remind（催促） | 毎時 | quote + due | 回答期限24時間前に未回答へ |
| coverage_check | 毎日 06:00 | agency | `expected_freq` に対し欠測ならアラート |
| close | 毎日 00:30 | tender | 提出期限を過ぎたら `終了` |

## 6. エラーコード

| コード | 意味 | 復旧 |
|---|---|---|
| `AUTH_REQUIRED` | ログイン/ICカードが必要 | 自動化しない。正式取得へ回す |
| `LAYOUT_CHANGED` | セレクタが空振り | **即アラート。最優先で修正** |
| `DOC_NOT_FOUND` | リンク切れ | 3回リトライ後、手動登録キューへ |
| `OCR_FAILED` | 画像品質が低い | 手動登録キューへ |
| `PARSE_INVALID` | JSONスキーマ違反 | 再実行、2回失敗で人へ |
| `RATE_LIMITED` | 相手先の制限 | バックオフして翌回へ |
| `OUT_OF_SCOPE` | 工事・自治体など対象外 | 登録のみ、解析しない |

`LAYOUT_CHANGED` の未対応が48時間続いたら、その機関のカバレッジをUIで「取得できていない」と明示する。**取れていないことを隠さない**のが信頼の条件。

## 7. 提案エンジン

配点（合計100）：資格区分20／営業品目20／等級15／競争参加地域15／予定価格10／残日数10／協力会社の保有10

- 資格区分・営業品目・等級のいずれか未充足 → `対象外`（理由必須）
- 80以上＝参加推奨、60〜79＝要確認
- 予定価格が非公表 → 5点（中立）とし理由に明記
- 協力会社点＝必要業種のうち登録会社がある業種の割合 × 10
- キーワード／除外キーワードは案件名＋仕様書本文に対して適用
- 再照合：条件セット変更時に `提案対象` `配信済` `既読` のみ作り直す

## 8. 通知

- 毎朝1通のダイジェスト（新着提案・今日の期限・未回答の見積）
- 即時通知は3つだけ：質問期限48時間前、提出期限48時間前、見積の返信受信
- 通知は「次にやること」を1つだけ書く。複数書くと読まれない

## 9. セキュリティ・法務

- 取得はアカウント不要の公開範囲に限定。ログイン内の自動操作は行わない（方針として明文化し、コネクタのコードレビュー基準にする）
- robots とサイトの利用条件を機関マスタに記録し、取得前に参照する
- 資料の再配布はしない。ユーザーには自社取得を案内する
- 個人情報：協力会社の担当者名・連絡先が対象。org単位で分離し、退会時に削除
- LINE連携はユーザー企業のアカウントで行う（当社アカウントから一斉送信しない）
