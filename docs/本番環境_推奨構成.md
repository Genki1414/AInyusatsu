# 本番環境の推奨構成

前提：Supabase を既に使っている／実装は Claude Code／運用は少人数／来年の事業譲渡に耐える構成。
**選定基準は「速く作れる」より「引き継げる・止まらない・説明できる」**です。

---

## 結論（この構成で進める）

| 層 | 採用 | 理由 |
|---|---|---|
| アプリ | **Next.js（App Router）＋ Vercel** | 既に使い慣れている。プレビュー環境が自動で立ち、Claude Code との相性が良い |
| DB・認証 | **Supabase（Postgres + Auth）** | 継続。RLS で企業ごとのデータ分離を DB 層で担保できる |
| 資料の保管 | **Supabase Storage（非公開バケット）** | 後述 |
| 全文検索 | **Postgres の全文検索（pgroonga または tsvector）** | 資料検索のために別サービスを立てない |
| ベクトル検索 | **pgvector（Supabase 標準）** | 過去案件の類似検索。DB内で完結 |
| ジョブ実行 | **pg-boss（Postgres ジョブキュー）＋ 常駐ワーカー1台** | 後述。ここが構成の肝 |
| 収集ワーカー | **Railway（または Fly.io）に Node + Playwright を常駐** | Vercel のサーバーレスでは Playwright と長時間処理が回らない |
| **収集端末** | **社内のWindows常時起動機＋ICカードリーダー** | 電子調達システムの資料取得にICカードとPINが必要。クラウドからは操作できない（→ `資料取得方針_v3.md`） |
| AI解析 | **Claude API** | PDF をそのまま渡せる。OCR を別に立てずに済む場合が多い |
| メール送信 | **Resend** | 実装が最も簡単 |
| メール受信 | **Postmark の Inbound（または Cloudflare Email Routing → Webhook）** | 見積の返信を取り込むため受信が必須 |
| LINE | **LINE Messaging API（公式アカウント）** | |
| 決済 | **Stripe** | 後述の課金設計を参照 |
| エラー監視 | **Sentry** | |
| 死活・欠測監視 | **Better Stack（旧 Betterstack Uptime）** | 収集が止まったことに気づけないのが最大のリスク |

**月額の目安：1.5〜2万円＋AI利用料**（Vercel Pro $20 / Supabase Pro $25 / Railway $10〜 / Resend $20 / Sentry 無料枠）。

---

## なぜ Vercel だけで完結させないのか

収集エンジンは **Playwright を使い、1回の実行が数分〜数十分**になります。
サーバーレス関数は実行時間の上限があり、ブラウザバイナリも重いため、ここだけは常駐プロセスにします。

```
Vercel（画面・API）
   │  ジョブを積む
   ▼
Supabase Postgres（pg-boss のジョブテーブル）
   ▲  ジョブを取り出す
   │
Railway の常駐ワーカー（Node + Playwright）
   └─ 巡回 → 資料取得 → Storage 保存 → Claude で解析 → DB 書き戻し
```

**ジョブキューを Redis ではなく Postgres（pg-boss）にする理由**：インフラが1つ減り、ジョブの状態を SQL で直接見られます。
障害時に「何が詰まっているか」を DB を覗くだけで判断できることは、少人数運用では決定的です。

代替案として GitHub Actions のスケジュール実行でも動きますが、**失敗の可視化とリトライを自前で作ることになる**ので、
最初から Railway の常駐ワーカーにしておくことを勧めます。

## 資料（PDF）の保管をどうするか

ここは技術より**方針が先**です。

### 方針：システムが取得した原本は、ユーザーにダウンロードさせない

理由は3つあります。

1. 発注機関の資料を第三者に再配布する形になり、**法的にグレー**
2. 「システムが取得した資料＝正式取得ではない」という設計思想と矛盾する
3. 原本を配ると、ユーザーが公式サイトで正式取得しなくなり、失格につながる

**ユーザーに提供するもの**：AIの解析結果（要約・参加資格・期限・必要業種・提出書類）、原文の短い引用と出典、そして**公告元URLへのリンク**。
原本の閲覧が必要なら、公式サイトへ誘導します。

### 保管の設計

| 対象 | 置き場所 | 権限 |
|---|---|---|
| 原本PDF・Excel | Supabase Storage の**非公開バケット** | service_role のみ。ユーザーには署名URLも発行しない |
| 抽出テキスト | Postgres（`tender_documents.extracted_text`） | 検索とAI解析の入力に使う |
| 解析結果 | Postgres（`tender_analyses`） | ユーザーに提供する唯一の成果物 |
| 引用（根拠） | 解析結果の中に短い引用として保持 | 原文の全文は持たない |

バケットは1つ、キーは `tenders/{tender_id}/{kind}_{sha256}.pdf`。
**同一ハッシュは再保存しない**（同じ資料が複数の機関から出ることがあります）。

容量が増えたら Cloudflare R2 への移行を検討します（転送量が無料）。ただし初年度は Supabase Storage で足ります。

### 保存期間

- 原本：解析完了から**1年**で削除（提出期限から1年でも可）。長く持つ理由がありません
- 抽出テキストと解析結果：保持（相場データと過去案件検索の資産になります）

## Supabase の使い方で必ず守ること

1. **RLS を全テーブルで有効にする。** `org_id` を持つテーブルは、必ず「自分の org のみ」のポリシーを書く
2. **案件マスタ（tenders）は全ユーザー共通なので、読み取りは全 org 許可・書き込みは service_role のみ**
3. **service_role キーはワーカーとサーバー側だけ**。ブラウザに絶対に出さない
4. **マイグレーションはファイルで管理**（Supabase CLI）。ダッシュボードで直接いじると、譲渡時に再現できなくなります
5. **バックアップ**：Supabase の日次バックアップに加えて、`tenders` `tender_analyses` `awards` は週1で外部にダンプ。これが事業の資産です

## 監視で必ず入れる3つ

1. **収集ジョブが完了しなかった** → 即通知
2. **コネクタのセレクタが空振り（LAYOUT_CHANGED）** → 即通知。**これを放置するとサービスが静かに死にます**
3. **機関ごとの欠測**（通常の公告頻度から外れた）→ 日次で通知

通知先はメールと、可能なら LINE か Slack。**朝5時に気づける状態**にしておきます。

### いまの実装（2026-08-29）

`notify-ops` ジョブが毎朝 6:20（JST）に、`ADMIN_EMAILS` あてへ1通送ります
（`apps/worker/jobs/notify_ops.ts`）。中身は上の3つに対応します。

| | 中身 |
|---|---|
| 1 | 直近24時間に失敗したジョブの名前（pg-boss の job テーブルから） |
| 2 | 失敗コード別の件数と、取るべき行動。48時間直っていないものは別枠で明示 |
| 3 | 機関ごとのカバレッジ（正常／欠測・未取得／遅延） |

**異常が無くても毎朝送ります。** 「異常があるときだけ送る」にすると、
ワーカーごと止まったときに何も届かず、いちばん危ない壊れ方を見逃します。
件名に状態を入れてあるので（`［AI入札部］正常` / `［AI入札部］要対応 3件`）、
開かずに判断できます。**届かない日があること自体が異常の合図です。**

リリース前に `pnpm --filter worker notify:ops` を1回叩いて、
実際に届くことを確かめてください。宛先と Resend の設定は、届いて初めて確認できます。

まだ入れていないもの：LINE / Slack への通知、失敗した瞬間の即時通知
（いまは翌朝までに気づく形）。

## ドメイン

お名前.com で取得後、**DNS は Cloudflare に向ける**ことを勧めます（管理画面が使いやすく、メール認証の設定が楽）。

必要な設定：
- Vercel 用の A/CNAME
- Resend 用の SPF・DKIM・DMARC（**これを設定しないと営業メールが迷惑メールに入ります**。最重要）
- メール受信用の MX（Postmark または Cloudflare Email Routing）

送信ドメインは、既存の事業と分けるか同じにするか決めてください。**分けることを勧めます**（新規ドメインからの大量送信は評判が低いので、送信は少量から段階的に増やす）。
