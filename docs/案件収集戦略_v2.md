## 1-2. 実際のレスポンス（叩いて確認済み）

APIを実際に叩いて返ってきたデータを確認しました。**当初の想定より取得できる情報が多い**ことが分かりました。

### 確認できた項目（1レコードあたり）

| 項目 | 例 | 用途 |
|---|---|---|
| キー（Base64） | `fukushima/tamura_city/2026/20260731_01361` を base64 化したもの | **デコードすると「県/機関/年/日付_連番」。重複排除キーの補助に使える** |
| 公告PDFのURL | `https://www.city.tamura.lg.jp/.../260731条件付き入札公告第250号.pdf` | **資料取得の入口** |
| 件名 | たむらクリーンセンターごみクレーン点検整備業務委託 (138.4KB) | 末尾にファイルサイズが付くので**除去が必要** |
| 日時①・日時② | `2026-07-07T19:07:43+09:00` / `2026-07-31T00:00:00+09:00` | **意味が未確定（下記）** |
| ファイル形式 | pdf | |
| ファイルサイズ | 141706 | |
| 都道府県コード・名 | `07` / 福島県 | **JISコード付き。地域の絞り込みが正確にできる** |
| 市区町村コード・名 | `072117` / 田村市 | 同上 |
| 地域 | 福島県田村市 | |
| 区分 | **役務 / 工事** | 物品・役務の絞り込みに使える |
| **本文** | 公告PDFから抽出された**テキスト全文** | **これが最大の発見** |

### 最大の発見：公告の本文全文が返ってくる

レスポンスに、**公告PDFから抽出されたテキストが丸ごと入っています。**
実際のサンプルでは、参加資格要件・質問期限・入札期間・開札日時・予定価格・最低制限価格まで、
公告の中身がすべてテキストで含まれていました。

つまり **AI解析の一次入力が、APIだけで手に入ります。**
「公告PDFをダウンロードしてOCRにかけて解析」という工程を、少なくとも公告レベルでは省略できます。

### ただし、資料取得は省略できません（重要）

KKJに含まれるのは**公告のみ**です。**入札説明書・仕様書・数量表・様式は含まれていません。**

これらは本部機能としてユーザーに提案を出すために**必ず取得します。** 理由は明快です。

| 資料 | これがないとできないこと |
|---|---|
| 入札説明書 | 参加条件・提出書類・手続きの確認。参加可否の判断ができない |
| 仕様書 | **必要な協力業種の判断ができない**（＝見積依頼が作れない） |
| 数量表 | **業種別に切り出して見積依頼に添付できない**（見積が集まらない） |
| 様式 | 提出書類チェックリストが作れない |

KKJの本文は「案件を早く見つけ、当たりを付ける」ためのものであり、**資料取得の代替ではありません。**

ただし、**資料が全種類揃わないことを理由に提案を止めることはしません。**
案件によっては入札説明書と仕様書しか存在しません。提案できる内容があれば提案し、
判定できない項目は「未判定」と明示します（→ `資料取得方針_v3.md`）。

そして、**取得した入札説明書・仕様書・数量表・様式のPDFも、すべてAI解析にかけます。**
公告だけを解析対象にする設計にはしません。

### 自治体の案件が普通に返ってくる

確認したサンプルは福島県田村市と山形県鶴岡市の案件でした。
**自治体が最初から収録されている**ことが実データで確認できたので、V2の自治体展開は
「資料取得の実装」だけの問題になります。

### 未確認で、必ず確かめること

1. **日時が2つあり、意味が確定できていません。**
   サンプルAでは①が公告日、②が開札日と一致しましたが、サンプルBでは①②とも公告日と同じでした。
   **締切の取り違えは失格に直結します。**仕様書で必ず確認し、**期限は本文または資料から取り直す**設計にしてください
2. 国の機関（府省・独法）の案件がどう返るか（サンプルはどちらも自治体だった）
3. パラメータ名の正確な仕様（日付での絞り込みができるか。**毎朝の巡回に必須**）
4. 1回のレスポンス件数とページングの方法
5. 件名末尾の `(138.4KB)` のような付随文字列の除去ルール

## 2. 戦略：2階建てにする

KKJ APIは**網**であって、**取得先ではありません。** 資料（仕様書・数量表・様式）は取れないからです。

```
第1層：案件の存在を知る（広く・浅く）
  └ KKJ API
      ・国・独法・自治体を横断
      ・毎日ポーリングして新規案件を検知
      ・機関名・件名・公告URL・期限を取得
      ・スクレイピング不要、実装1日

第2層：資料を取得して解析する（狭く・深く）
  └ 調達ポータル ＋ 各機関サイト ＋ ICカード端末
      ・第1層で見つけた案件のうち、
        「いずれかの顧客の条件に該当しうるもの」だけ
      ・公告・入札説明書・仕様書・数量表・様式を取得
      ・AI解析にかける
```

**この構造にすると、カバレッジ問題がほぼ解決します。**
「機関ごとにコネクタを書き、葉のカバレッジを95%にする」という重い計画が、
「APIで網を張り、取りに行く先だけコネクタを書く」に変わります。

## 3. 何が変わるか

| | 旧計画 | 新計画 |
|---|---|---|
| 案件の発見 | 機関ごとにスクレイピング | **KKJ APIで横断取得** |
| 機関マスタの役割 | 巡回先のリスト | **カバレッジ照合の母集団**（APIの取りこぼし検知） |
| 第1週の実装 | 調達ポータルのスクレイパ | **KKJ APIクライアント**（半日）＋ 調達ポータルの資料取得 |
| 自治体への拡張（V2） | 自治体ごとにコネクタ | **APIに既に含まれている**（資料取得だけ別途） |
| サイト構造変更のリスク | 機関の数だけある | 資料取得先だけに縮小 |

**自治体がAPIに含まれている**ことは、V2の計画を根本から変えます。
案件の発見だけならコネクタを書かずに全国に広がるので、
「自治体は資料取得の実装ができた地域から順に開放する」という進め方ができます。

## 4. 注意すべき点（ここを誤ると事故る）

1. **KKJは一次ソースではありません。** 「すべての情報を保証しない」と明記されています。
   **期限などの重要項目は、必ず発注機関の原本（取得した資料）から取り直す**こと。
   KKJの値は「案件を見つけるための手がかり」として扱い、解析結果はあくまで資料から作ります。

2. **1日遅れます。** 提出期限が近い案件を取りこぼす可能性があるため、
   **調達ポータルの巡回は併用します**（こちらは即日）。KKJだけに寄せない。

3. **利用条件の遵守。** サイト内（フッターや「情報の出どころ」ページ）に、
   本APIを利用している旨とリンクを必ず入れます。**規約・LPの制作物にも反映が必要です。**

4. **APIのURLは変わりうる。** 監視対象に入れ、レスポンス形式が変わったら即アラート。

5. **重複排除。** KKJ経由と調達ポータル経由で同じ案件が入るので、
   既存の重複排除キー（機関＋公告番号＋提出期限）で必ず統合します。

## 8. 実レスポンスの分析（実際に叩いて確認）

APIを叩いた結果、1件あたり次の項目が返ることが分かりました。**想定よりはるかに使えます。**

| # | 項目 | 例 | 使い道 |
|---|---|---|---|
| — | ヘッダ | `.0 59771 1` | 2番目は**総ヒット件数**と思われる（約6万件）。ページングの判断に使う |
| 1 | 連番 | `1` | |
| 2 | **ID（Base64）** | デコードすると `fukushima/tamura_city/2026/20260731_01361` | **都道府県／機関／年／日付＋連番**。一意キーとして使える |
| 3 | **公告PDFのURL** | 発注機関サイトの直リンク | **資料取得の一次入口** |
| 4 | 件名 | ファイルサイズ付き | |
| 5 | 日時 | `2026-07-07T19:07:43+09:00` | 登録日時と思われる |
| 6 | 形式 | `pdf` | |
| 7 | サイズ | バイト数 | |
| 8-11 | **都道府県コード・名／市区町村コード・名** | `07` 福島県 `072117` 田村市 | 全国地方公共団体コード。**地域の絞り込みが正確にできる** |
| 12 | 地域名 | `福島県田村市` | |
| 13 | 日付 | `2026-07-31` | 公告日と思われる |

| 15 | 件名（再掲） | | |
| 16 | **公告本文のテキスト全文** | PDFから抽出済みの本文 | **AI解析の一次入力にそのまま使える** |

### ここから分かる、設計上の要点

1. **本文テキストが入っている。** これが最大の収穫です。
   公告PDFを自前でダウンロードしてOCRにかけなくても、**参加資格・期限・履行場所・業務概要をAIで抽出できます。**
   第2週に予定していた「取得→OCR→解析」の前段が、案件の一次判定については不要になります。

2. **ただし構造化されているのは種別と地域まで。** 提出期限・開札日・参加資格・等級は
   **本文の中にあるだけで、項目としては返ってきません。** AI解析は必須です。
   ゴールドセットによる精度測定の重要性は変わりません。

3. **仕様書・数量表・様式は含まれません。** 公告本文のみです。
   見積依頼に必要な数量表は、引き続き調達ポータルや発注機関サイトから取得します。

4. **総ヒットが約6万件。** 日付で絞らずに全件を取ると破綻します。
   **「登録日＝昨日」で毎日差分を取る**設計にしてください。1件あたりのデータ量も大きい（本文込み）ため、
   件数を絞ることが必須です。

5. **自治体の案件が実際に入っている**（田村市・鶴岡市で確認）。
   V2の自治体展開が、案件の発見に関しては追加実装なしで可能です。

### まだ確認が必要なこと（4つ）

| # | 確認すること | 方法 |
|---|---|---|
| 1 | **国の機関の案件も返るか** | 機関名に「財務局」「地方整備局」などを指定して検索する。自治体だけだと今回のV1では使えない |
| 2 | **日付で絞れるか**（登録日 from-to） | 仕様書のパラメータを確認。ここが無いと毎朝の差分取得が作れない |
| 3 | **ページングの方法**（開始位置・取得件数） | 同上。6万件を扱うには必須 |
| 4 | XMLのタグ名 | ブラウザで「ページのソースを表示」すると、各項目のタグ名が見える |

**1番が最優先です。** 国の案件が返らないなら、V1ではKKJは補助的な位置づけになり、
調達ポータルの巡回が主役に戻ります。逆に返るなら、第1週の実装は大きく楽になります。
