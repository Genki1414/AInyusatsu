# ローカル実行手順（KKJ同期・調達ポータル巡回・落札実績オープンデータ取り込み）

ワーカー（`apps/worker`）の各ジョブを、自分のPCから手動で1回ずつ実行するための手順。
本番のスケジュール実行（pg-boss常駐）はタスク1-5以降の別範囲であり、ここでは対象にしない。

## 0. 前提条件

- リポジトリのルートで `pnpm install` 済みであること
- `supabase db push` などで、対象のSupabaseプロジェクトに `supabase/migrations` が適用済みであること
- 調達ポータル（GEPS）の巡回のみ、Playwrightのブラウザ本体が必要。初回に1度だけ実行する

  ```
  pnpm --filter worker exec playwright install chromium
  ```

## 1. 環境変数

`apps/worker/.env.example` をコピーして `apps/worker/.env.local` を作成し、値を埋める
（`.env.local` は `.gitignore` で除外済み。コミットされない）。

```
cp apps/worker/.env.example apps/worker/.env.local
```

| 変数名 | 用途 | 必須になるジョブ | 備考 |
|---|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabaseプロジェクトの URL | 全ジョブ共通 | Supabaseダッシュボード → Project Settings → API |
| `SUPABASE_SERVICE_ROLE_KEY` | service_roleキー | 全ジョブ共通 | 同上。**クライアントに渡さない・GitHub等にコミットしない** |
| `KKJ_API_URL` | KKJ検索APIのエンドポイント | KKJ同期（省略可） | 既定値 `http://www.kkj.go.jp/api/` のため、通常は設定不要 |
| `AWARDS_OPEN_DATA_BASE_URL` | 落札実績オープンデータzipのダウンロードURL（既定値あり） | 落札実績取り込み（省略可） | 既定値 `https://api.p-portal.go.jp/pps-web-biz/UAB03/OAB0301?fileversion=v001&filename=` のため、通常は設定不要 |
| `GEPS_CONTACT_COMPANY` | 資料DL時の商号又は名称 | 調達ポータル巡回 | 本部（自社）の名義。docs/資料取得方針_v3.md §0-1参照 |
| `GEPS_CONTACT_NAME` | 資料DL時の氏名 | 調達ポータル巡回 | 同上 |
| `GEPS_CONTACT_TEL` | 資料DL時の電話番号 | 調達ポータル巡回 | 同上 |
| `GEPS_CONTACT_EMAIL` | 資料DL時のメールアドレス | 調達ポータル巡回 | 同上 |
| `TENDER_DOCUMENTS_BUCKET` | 資料の保存先バケット | 調達ポータル巡回・資料テキスト抽出 | 既定値 `tender-documents`。Supabase Storageに未作成なら先に作成する |
| `ANTHROPIC_API_KEY` | Claude APIのキー | AI解析スモークテスト | [console.anthropic.com](https://console.anthropic.com/) で発行 |

## 2. 実行コマンド

> **コピーするときの注意（Windows）**
> 以下のコマンドには `#` 以降に説明を付けているが、**Windowsのコマンドプロンプトは
> `#` をコメントとして扱わない**。説明ごと貼り付けると `#` と説明文がそのまま引数になり、
> 「HTTP 500」「Invalid time value」のような、原因の分からない失敗になる。
> **`#` の手前までをコピーすること。**
>
> なお各コマンドは想定より多い引数を受け取った時点で止まり、その旨を表示する
> （`引数が多すぎます（2個："#" "説明"）`）。

すべてリポジトリのルートから実行する。日付・年を省略した場合の既定値は各コマンドの説明を参照。

### KKJ（官公需情報ポータル）の同期

```
pnpm --filter worker kkj:sync                    # 前日（JST）の公告日ぶん
pnpm --filter worker kkj:sync -- 2026-07-31       # 日付を指定する場合
```

### 調達ポータル（GEPS）の巡回

```
pnpm --filter worker geps:crawl                            # 前日（JST）の公開開始日ぶん
pnpm --filter worker geps:crawl -- 2026-07-31               # 日付を指定する場合
pnpm --filter worker geps:crawl -- 2026-07-01 2026-07-31    # 範囲を指定する場合（最大31日）
```

ブラウザが起動して画面操作を行うため、KKJより時間がかかる（1案件ごとに検索やり直し＋詳細取得＋資料DL）。

### 落札実績オープンデータの取り込み

```
pnpm --filter worker awards:import -- full 2026        # 全件（年度ごと）
pnpm --filter worker awards:import -- diff 2026-07-31   # 差分（日ごと）。省略時は前日（JST）
```

差分は対象日のファイルが存在しない（404）場合があるが、その場合は `no_data` として正常終了する
（エラーではない）。

### 資料のテキスト抽出（PDF）

調達ポータル巡回で資料（Storage）が保存された後に実行する。

```
pnpm --filter worker documents:extract-text          # 既定：最大50件
pnpm --filter worker documents:extract-text -- 200    # 件数を変える場合
```

テキストPDFはそのまま抽出、画像PDF（スキャン）はOCR（`tesseract.js`・日本語）する。
OCRは初回実行時に言語データをネットワーク経由で取得するため、KKJ・GEPSより時間がかかることがある。
対象は現時点で`.pdf`のみ（Word/Excel等は未対応・別タスク）。

### market_rates（相場の集計キャッシュ）の再計算

落札実績の取り込み後に実行する（awardsのデータを集計する側のジョブのため）。

```
pnpm --filter worker market-rates:refresh              # 既定：直近24か月
pnpm --filter worker market-rates:refresh -- 12         # 対象月数を変える場合
```

### AI解析のスモークテスト（タスク2-3）

資料のテキスト抽出（`tender_documents.extracted_text`が埋まっている資料）が1件以上ある状態で実行する。
プロンプト「基本情報と期限」を実際にClaude APIへ1回投げ、Zodスキーマを通るか確認する。

```
pnpm --filter worker ai:smoke-test                    # extracted_textがある資料のうち最初の1件
pnpm --filter worker ai:smoke-test -- <tender_documents.id>   # 対象を指定する場合
```

### AI解析結果の保存（タスク2-4・2-5・2-3b）

1案件ぶんのテキスト抽出済み資料を使って、プロンプト1（基本情報と期限）・2（参加資格と参加条件）・
3（数量表の構造化と業種割当）・4（提出書類）・5（注意事項）をまとめて実行し、
`tenders`/`tender_analyses`/`tender_forms`/`tender_lots`へ保存する。あわせて期限の前後関係・
和暦変換ミスの検出を行い、違反があれば`tenders.needs_review`を立てる。

```
pnpm --filter worker analyze:tender -- <tenders.id>
```

対象の`tenders.id`は、資料のテキスト抽出まで済んでいる案件から選ぶ。

```sql
select t.id, t.code, t.name, count(d.id) as extracted_docs
from tenders t join tender_documents d on d.tender_id = t.id
where d.extracted_text is not null
group by t.id, t.code, t.name
limit 5;
```

### 解析待ちの案件をまとめてAI解析する

`collect_status = 取得済` かつテキスト抽出まで済んだ案件を、提出期限が近い順にまとめて解析する。
**費用がかかるのはこのコマンドだけ**（実測 約69円/件）。実行前に見込み額が表示される。

```
pnpm --filter worker analyze:pending              # 既定の50件（約3,500円）
pnpm --filter worker analyze:pending -- 200        # 件数を指定
pnpm --filter worker analyze:pending -- 200 90     # 公告日が90日以内のものだけ
pnpm --filter worker analyze:pending -- 0          # 何もしない（動作確認用）
```

第2引数は公告日の上限（日数）。提出期限はAI解析で初めて埋まるため、解析前の案件は
提出期限が null で「期限切れ」として除外できない。長く解析を止めていた後に流すときは、
これを付けないと締め切り済みの案件にも費用がかかる。既定では絞らない（推測で対象を減らさない）。

1件が失敗しても残りは続く（失敗理由は案件の `failure_code` / `failure_reason` に残る）。
解析が終わった案件は、このコマンドの最後に自動で `公開中` へ進む。

解析待ちが何件あるかは次で分かる。

```sql
select count(distinct t.id)
from tenders t
join tender_documents d on d.tender_id = t.id
where t.collect_status = '取得済' and d.extracted_text is not null;
```

### 発注機関の欠測チェック（実装仕様書 §5 coverage_check）

機関ごとに `expected_freq`（daily / weekly / monthly）と `last_success_at` を比べ、
想定した間隔で取得できているかを確かめる。

```
pnpm --filter worker coverage:check
```

想定間隔を過ぎたら「遅延」、倍を過ぎたら「欠測」。1回の巡回失敗で警報を鳴らさないため
二段階にしている。`expected_freq` が無い機関は判定しない（機関が出していないだけかもしれない）。

結果は「今日やること」の画面にも出る。`last_success_at` は KKJ同期・調達ポータル巡回が
案件を取得できたときに更新される。

### 案件の公開・終了（実装仕様書 §5 close）

AI解析が終わった案件（`collect_status = 解析完了`）を `公開中` にし、提出期限を過ぎた案件を
`終了` にする。提案（match）は `公開中` の案件だけを見るので、これを走らせないと提案は0件のまま。

```
pnpm --filter worker tenders:lifecycle
```

提出期限が取れていない（null）案件は `終了` にしない（推測しない）。件数だけ警告に出る。

常駐ワーカーでは `tender-lifecycle` として 00:30 / 10:30 / 18:30 に自動で走る。
また `analyze-pending` の最後にも呼ばれるので、解析が終わった案件はその場で公開される。

## 3. 成功判定（何を見れば成功したと言えるか）

各コマンドは標準出力にJSONの実行結果を出す（`status`/`found`/`merged`等）ので、まずそれを確認する。
そのうえで、Supabase Studio（`supabase start`していればローカルは `http://127.0.0.1:54323`。
リモートプロジェクトならダッシュボードのTable Editor）で以下を確認する。

### KKJ同期

- `crawl_runs`：`connector_id = 'kkj'` の最新行の `status` が `completed`（失敗時は `failed`）。
  `found`（KKJから取得した件数）と `merged`（tendersへ反映できた件数）を確認。
  `merged` が `found` より少ない場合は、機関名（`OrganizationName`）が空でスキップされた案件がある
  （`failed` 列がスキップ件数）
- `tenders`：`connector_id = 'kkj'` で絞り込み、`notice_date` が指定日になっている行が増えていること
- `crawl_errors`：`run_id` が上記 `crawl_runs.id` の行が無いこと（あればエラー内容を確認）

```sql
select * from crawl_runs where connector_id = 'kkj' order by started_at desc limit 5;
select count(*) from tenders where connector_id = 'kkj' and notice_date = '2026-07-31';
```

### 調達ポータル（GEPS）巡回

- `crawl_runs`：`connector_id = 'geps'` の最新行の `status` が `completed` または
  `truncated`（500件ちょうどで打ち切り検知。要対応）
- `tenders`：`connector_id = 'geps'` で増えていること
- `tender_documents`：対象案件の `tender_id` に紐づく行があり、`fetched = true`・`storage_key` が
  埋まっていること。Supabase StorageのバケットにもファイルがあることをStudioの Storage 画面で確認
- 標準出力の `skipped`（詳細画面から調達案件番号を取得できずスキップした件数）が0でなければ、
  `crawl_errors`（`code = 'PARSE_INVALID'`）に該当案件が記録されているので、どの案件で
  失敗したか確認する

```sql
select * from crawl_runs where connector_id = 'geps' order by started_at desc limit 5;
select t.code, t.name, count(d.id) as doc_count
from tenders t left join tender_documents d on d.tender_id = t.id
where t.connector_id = 'geps' and t.notice_date = '2026-07-31'
group by t.id, t.code, t.name;
```

### 落札実績オープンデータの取り込み

- `award_imports`：最新行の `status` が `succeeded`（差分で対象日のファイルが無かった場合は
  `no_data`）。`rows_total`/`rows_upserted`/`rows_skipped` を確認
- `awards`：想定件数ぶん行が増えている（`source_batch` 列で今回の取り込み分を絞り込める）

```sql
select * from award_imports order by created_at desc limit 5;
-- source_batchはzipファイル名がそのまま入る（例: 全件2026年なら successful_bid_record_info_all_2026.zip、
-- 差分2026-07-31なら successful_bid_record_info_diff_20260731.zip）
select count(*) from awards where source_batch = 'successful_bid_record_info_all_2026.zip';
```

### 資料のテキスト抽出

- `tender_documents`：対象資料の `extracted_text` が埋まっていること。`ocr_used = true` の行は
  OCR経由（`page_count` も埋まる）
- 失敗した資料は `extract_error` にエラーメッセージが入る（`succeeded`/`failed`の内訳は標準出力のJSON参照）

```sql
select kind, extracted_text is not null as extracted, ocr_used, extract_error
from tender_documents
where fetched = true and storage_key ilike '%.pdf'
order by fetched_at desc
limit 20;
```

### market_rates再計算

**現状、`groupsUpserted` は 0 になるのが正常です。** 落札実績オープンデータCSVには予定価格・
品目分類の列が無く、落札率が算出できないため（`docs/reference/落札実績オープンデータ_列定義（推定）.md` §1参照）。エラーなく実行が終わればOKです。

```sql
select count(*), max(updated_at) from market_rates;
```

### AI解析結果の保存

- `tenders`：解析前に空欄だった項目（提出期限・質問期限・開札日時・資格区分・予定価格等）が
  埋まっていること。**すでに値が入っていた項目（コネクタが確定させた項目）は変わっていない**
  はずなので、実行前後で差分を確認する
- `tender_analyses`：対象案件の行が増えており、`version`が1つ進んでいること。`raw`列に
  5プロンプトぶんの生出力（`quote`/`source`を含む）が入っていること。`trades`列に
  業種サマリー（`trades_summary`）が入っていること
- `tender_forms`：様式が抽出された案件では行が入っていること（無ければ0件でもエラーではない）
- `tender_lots`：数量表がある案件では行が入り、`trade`（業種）が付いていること。無い案件では
  `no_quantity_table: true`（標準出力のJSONでは分からないので`tender_analyses.raw`で確認）で0件でもエラーではない
- `tenders.needs_review`：標準出力の`needsReview`/`reviewReasons`と一致していること。
  期限の前後関係がおかしい案件（意図的に前後を入れ替えた資料等）で試すと確認しやすい

```sql
select version, model, jsonb_array_length(qualifications) as qual_count,
  jsonb_array_length(notes) as notes_count, jsonb_array_length(trades) as trades_count, created_at
from tender_analyses
where tender_id = '<tenders.id>'
order by version desc;

select name, source, required, note from tender_forms where tender_id = '<tenders.id>';
select line_no, item, spec, qty, unit, trade, confidence from tender_lots
where tender_id = '<tenders.id>' order by line_no;
select needs_review, review_reasons from tenders where id = '<tenders.id>';
```

### AI解析のスモークテスト

- 標準出力に、`docs/AI解析プロンプト集.md` §1の出力スキーマ通りのJSONが表示されること
- `value`が入っている項目には`quote`（原文引用）と`source`（出典）が一緒に入っていること
  （出典のない抽出はUIで「未確認」として扱う方針のため、ここが空ならプロンプトか資料側を疑う）
- スキーマ不一致で再試行した場合は`スキーマ不一致（再試行します）`が標準エラー出力に出る。
  2回とも失敗すると`ParseInvalidError`で終了する
