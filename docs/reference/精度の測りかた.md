# 精度の測りかた（タスク2-6 ゴールドセット）

AI解析が正しく読めているかを、人が作った正解と突き合わせて数字で出す。

## なぜ測るか

解析にはお金がかかる（実測 約69円/件・全体で月20万円規模）。
**精度を測らずに本番で回すと、間違った期限で提案し続けることになる。**
期限の誤りは失格に直結する（CLAUDE.md 最重要の前提5）ので、
ここだけは「だいたい合っている」では済まない。

## 目安（実装指示書 §4）

| 指標 | 目安 | なぜその水準か |
|---|---|---|
| 期限 | **100%** | 1件でも外すと、その顧客は入札に参加できない |
| 参加資格 | 95% | 外すと「参加できない案件」を提案してしまう |
| 業種F1 | 0.85 | 見積依頼の相手を選ぶのに使う。多少ずれても人が直せる |

## 手順

### 1. 解析する（費用がかかる）

```
pnpm --filter worker analyze:pending -- 20
```

**約1,400円**（69円 × 20件）。実行前に見込み額が表示される。

### 2. 確認用のファイルを作る

```
pnpm --filter worker goldset:template
```

`apps/worker/goldset/goldset.json` ができる。20件ぶんの**保存されている値と引用**が並ぶ。

**選ばれるのは、解析した日時が新しい20件。** 測りたいのは「いまのプロンプトの実力」で、
公告日の新しい順に選ぶと、古いプロンプトで解析した案件が混ざってしまう
（直す前と直したあとを1つの数字に混ぜない）。

**すでにファイルがあるときは作り直さない**（書き込んだ正解が消えるため）。

書き上げた `goldset.json` は**コミットする**。公告を1件ずつ読んで作る正解なので、
失うと同じ作業をやり直すことになる。

### 3. 引用を読んで、合っているか判断する

ファイルには**保存されている値と、その根拠になった引用・出典**が入っている。
**原文を開く必要はほとんどない。**

```json
{
  "tenderName": "庁舎清掃業務",
  "tenderId": "...",
  "sourceUrl": "https://...",
  "checked": [],
  "expected": {},
  "保存されている値": {
    "提出期限": {
      "値": "2026-09-25 17:00",
      "引用": "入札書の提出期限は令和8年9月25日午後5時とする。",
      "出典": "入札説明書 p.3"
    },
    "質問期限": { "値": "（無し）", "引用": "（引用なし＝未確認）", "出典": "（出典なし＝未確認）" }
  }
}
```

#### 出しているのは「AIの答え」ではなく「保存されている値」

`goldset:measure` が突き合わせるのは `tenders` の列、つまり**製品が実際に使う値**。
テンプレートにAIの生の抽出値を出すと、生の値と保存値がずれていても
「合っていた」と印が付き、その印は保存値のほうに適用されてしまう。
**書き込みの途中でずれる不具合を見逃す**（実際にタイムゾーンで起きた）。

そこで値は保存値を日本時間で出す。生の抽出値とずれていたら `注意` が付く。

```json
"注意": "AIは「2026-09-24T17:00（日本時間）」と読み取りましたが、保存されている値は「2026-09-25 02:00」です。..."
```

`注意` が出たら `pnpm --filter worker deadlines:repair`（既定は下見）で入れ直せる。
解析はやり直さないので費用はかからない。

判定は解析と同じ関数（`toJstTimestamp`）を使う。「日本時間に固定する」規則を
2か所に書くと、片方だけ直したときに食い違う（実際、日付だけの期限を取りこぼした）。

やることは2つだけ。

**（1）確認した項目を `checked` に書く**（合っていた項目も含めて）

```json
"checked": ["期限"]
```

| 書ける値 | 意味 |
|---|---|
| `"期限"` | 提出期限・質問期限・開札 |
| `"参加資格"` | 資格区分・営業品目・等級・競争参加地域 |
| `"業種"` | 数量表から割り当てた業種 |
| `"すべて"` | 上の全部 |

項目名を直接書いてもよい（`"submitDeadline"` など）。

**（2）間違えていた項目だけ `expected` に正しい値を書く**

```json
"checked": ["期限"],
"expected": { "submitDeadline": "2026-09-25T17:00:00+09:00" }
```

**合っていた項目は何も書かなくてよい。** これで作業は「引用を読む」だけになる。

#### 2つの原則

- **`checked` が空の案件は1項目も測らない。** 見ていないものを正解に数えると、数字が意味を失う
- **「引用なし＝未確認」と出ている項目は、必ず原文で確かめる。** 根拠が無い抽出は信用しない
  （CLAUDE.md 最重要の前提3）

#### この方法の限界

答えを見せずに書かせるほうが、測定としては正確。**引きずられる可能性は残る。**

それでもこの形にしたのは、20件×8項目を原文から書き写す作業では現実に誰もやらず、
**測らないことのほうが害が大きい**と判断したため。
代わりに「引用が根拠として成立しているか」を見る形にし、引用が無い項目は
原文確認に回るようにしてある。

**期限だけは、引用が付いていても原文と照らす価値がある。** 失格に直結するため。

書き上げた `goldset.json` は**コミットする**。

### 4. 測る

```
pnpm --filter worker goldset:measure
```

```
20件を突き合わせました。

■ 精度
  期限　　　　　　 95.0%（19/20）  目安 100.0%  届いていない
  参加資格　　　　 96.0%（24/25）  目安 95.0%   届いている
  業種F1　　　　　 0.88            目安 0.85    届いている

■ 間違えたところ
  庁舎清掃業務
    提出期限：正 2026-09-25 17:00 ／ AI 2026-09-26 02:00
```

**間違えた案件は必ず原文を確認する。** 9時間ずれていればタイムゾーンの取り違え、
日付ごと違えば読み取りの誤り。原因によって直す場所が変わる。

## 測っていないものは「届いている」と言わない

書かなかった項目は `—` と出る。0/0 を 100% と見せない。
測っていないのに「達成」と言うと、次に見た人が判断を誤る。
