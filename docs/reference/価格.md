## 決まっていないこと

### 1. 500通という数字の根拠（弱い）

**費用の心配は無い。** Playwrightで送るので1通あたりの変動費はほぼゼロ。
500通という数字は**費用から決めたものではない**。

そのため、実際に使われ方を見てから見直す前提で置く。

- 500通で足りるのか（1業種の開拓で何社に当たるのか）が分かっていない
- 少なすぎれば売り文句にならず、多すぎれば送りすぎの事故が増える

**金額ではなく、送りすぎの被害でこの上限を考えること。**
相手は将来の協力会社で、雑に大量送信すると関係が始まらない。

### 2. 500通を超えたらどうするか

止めるのか、追加で課金するのか、超過を許すのか——**ここはまだ決めていない。**

**通数を数える仕組みは実装済み。** 営業AI側の`GET /api/tenant/quota`
（`senders.py._check_quota()`と同じ直近30日ローリング計算）をアダプタ`getQuotaStatus()`
で読める。500通に達すると営業AI側の送信自体がそこで止まる（`form_send_log`を
直接見る必要はない）。案件の見積依頼タブで「今月の残り送信可能数」として表示もしている
（T55）。500通/月ちょうどで追加課金の判断をする画面・Stripe決済は
**決済は後回しにするユーザー決定**（2026-08-28）でまだ無い（`purchaseQuota()`
アダプタのみ用意済み）。

### 3. ログイン追加に必要な実装

**追加も本部が発行する**（ユーザー決定 2026-08-28）。顧客は画面から依頼を出すだけ。
請求書払いで、料金が発生する操作を顧客が自分で完了できてはいけないため。

```
顧客：ご契約の画面から「アカウントの追加を依頼する」
  ↓
本部：/admin に依頼が並ぶ → 内容を確認して発行 → 初期パスワードを本人へ伝える
  ↓
請求：翌月から 1つあたり 月5,000円
```

**いまは1組織1ログイン。** 実装が要るのは次の3つ。

- **顧客側の依頼フォーム**（追加する人の氏名・メールアドレス）
- **本部側の依頼一覧**と、そこから発行する導線
- **既存の組織に2人目を足す仕組み**

3つ目に落とし穴がある。いまは `auth.users` に行が入るたびに
`handle_new_user()` が**新しい組織を作る**（`20260803000001_auth_signup_trigger.sql`）。
そのまま2人目を作ると、同じ会社なのに別の組織ができて、案件も協力会社も見えない。
既存の組織に紐づける経路を分けて作る必要がある。

あわせて、いま何人いるか・請求がいくらになるかを両方の画面に出すこと。
**気づかないうちに人数が増えて請求が上がる**のがいちばん困る。

## 協力会社の開拓の流れ（2026-08-28 決定）

```
AI入札部：案件から不足している業種を判定
  ↓
AI入札部：営業AIの登録企業から候補を選ぶ（業種・地域で絞る）
  ↓
AI入札部：営業AIに送信先リストを作る
  ↓
利用者：送信ボタンを押す        ← 人がやるのはここだけ
  ↓
営業AI：問い合わせフォームへ送信
```

**送信を呼ぶのは、利用者がボタンを押した1回きり。**
定期実行やジョブから送信を呼ばない（CLAUDE.md「やらないこと」）。

## リリース時にどうするか

**基本プラン1本で出すのを勧める。**

- ログイン追加は**引き合いが出てから**作る（依頼フォーム・本部側の一覧・
  既存組織への追加が要る）。それまでは電話やメールで受けて、本部が手で発行すればよい
- 営業AIの500通は、営業AI側の業種・企業がまだ揃っていないので
  そもそも使えない。**枠だけ約束して後から用意するのは危ない**

営業AIの準備ができるまでは、**月45,000円・ログイン1つ・営業AI無し**で売り、
営業AIが使えるようになった時点で500通込みに切り替えるのが素直。
その場合、先に契約した顧客の扱い（値上げしないか）を先に決めておくこと。
