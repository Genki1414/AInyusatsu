## 支払いと解約の決まり（2026-08-29 決定）

**前払いにする。** 利用する月の前月末日までに、その月分を振り込んでもらう。

**解約の予告は要らない。** 翌月分を払わなければ、その月から提供しない。
それで契約は終わる。お客様から解約の連絡を受ける必要も、こちらが承る手続きも無い。

この2つは組みで意味を持つ。後払いにすると「使われたのに払われない月」が必ず出るが、
前払いなら**未収が構造的に発生しない**。督促も、止めるかどうかの判断も要らない。

止めるのは `org_access` を「停止」にするだけ（`/admin/accounts`）。
理由は「お支払いの確認が取れていないため」を選ぶ。

**請求書を出す時期に注意。** 前月末が期限なので、請求書はその前に届いている必要がある。
月初に出すのでは間に合わない。

規約の第5条・第10条・第11条に同じことを書いてある（`/terms`）。

## 決まっていないこと

### 1. 500通という数字の根拠（弱い）

**費用の心配は無い。** Playwrightで送るので1通あたりの変動費はほぼゼロ。
500通という数字は**費用から決めたものではない**。

そのため、実際に使われ方を見てから見直す前提で置く。

- 500通で足りるのか（1業種の開拓で何社に当たるのか）が分かっていない
- 少なすぎれば売り文句にならず、多すぎれば送りすぎの事故が増える

**金額ではなく、送りすぎの被害でこの上限を考えること。**
相手は将来の協力会社で、雑に大量送信すると関係が始まらない。

### 2. 500通を超えたらどうするか

止めるのか、追加で課金するのか、超過を許すのか。
**通数を数える仕組みも、まだ無い。** 営業AI側の `form_send_log` を見る必要がある。

### 3. ログイン追加に必要な実装

**追加も本部が発行する**（ユーザー決定 2026-08-28）。顧客は画面から依頼を出すだけ。
請求書払いで、料金が発生する操作を顧客が自分で完了できてはいけないため。

```
顧客：ご契約の画面から「アカウントの追加を依頼する」
  ↓
本部：/admin に依頼が並ぶ → 内容を確認して発行 → 初期パスワードを本人へ伝える
  ↓
請求：翌月から 1つあたり 月5,000円
```

**実装済み**（2026-08-29）。

- 顧客側の依頼フォーム：ご契約の画面の「ログイン」
- 本部側の依頼一覧：`/admin/accounts` の発行フォームのすぐ下
- 既存の組織に2人目を足す仕組み：`20260829000001_account_requests.sql`

落とし穴は3つ目にあった。`handle_new_user()` は `auth.users` に行が入るたびに
**必ず新しい組織を作っていた**（`20260803000001_auth_signup_trigger.sql`）。
そのまま2人目を作ると、同じ会社なのに別の組織ができて、案件も協力会社も見えない。

`raw_user_meta_data` に `org_id` があればその組織へ参加し、無ければこれまでどおり
新しい組織を作るようにした。1人目の発行は挙動を変えていない。
**存在しない組織IDが来たら例外にする**（黙って新しい組織を作ると、
ログインできるのに何も見えないアカウントができる）。

いま何人いるか・発行するといくらになるかは、**両方の画面に出してある**。
**気づかないうちに人数が増えて請求が上がる**のがいちばん困るため。

## 協力会社の開拓の流れ（2026-08-28 決定）

```
AI入札部：案件から不足している業種を判定
  ↓
AI入札部：営業AIの登録企業から候補を選ぶ（業種・地域で絞る）
  ↓
AI入札部：営業AIに送信先リストを作る
  ↓
利用者：送信ボタンを押す        ← 人がやるのはここだけ
  ↓
営業AI：問い合わせフォームへ送信
```

**送信を呼ぶのは、利用者がボタンを押した1回きり。**
定期実行やジョブから送信を呼ばない（CLAUDE.md「やらないこと」）。
