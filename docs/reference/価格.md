## 決まっていないこと

### 1. 営業AIの500通をどう用意するか

**いまの実装と食い違っている。**

`docs/reference/営業AI連携.md` は「**顧客が自分の営業AIアカウントで行う**」前提で作ってある
（顧客が自分でURLとAPIキーを設定する）。基本プランに500通を含めるなら、
本部が営業AIの枠を用意して顧客に渡すことになる。設計が変わる。

決める必要があるもの：

- 本部が顧客ごとに営業AIのテナントを作って、APIキーを渡すのか
- それとも本部のテナントを共有し、送信元だけ顧客名義にするのか
- **500通の原価はいくらか**（営業AI側のフォーム送信の実費。未確認）

### 2. 500通を超えたらどうするか

止めるのか、追加で課金するのか、超過を許すのか。
**通数を数える仕組みも、まだ無い。** 営業AI側の `form_send_log` を見る必要がある。

### 3. ログイン追加に必要な実装

**追加も本部が発行する**（ユーザー決定 2026-08-28）。顧客は画面から依頼を出すだけ。
請求書払いで、料金が発生する操作を顧客が自分で完了できてはいけないため。

```
顧客：ご契約の画面から「アカウントの追加を依頼する」
  ↓
本部：/admin に依頼が並ぶ → 内容を確認して発行 → 初期パスワードを本人へ伝える
  ↓
請求：翌月から 1つあたり 月5,000円
```

**いまは1組織1ログイン。** 実装が要るのは次の3つ。

- **顧客側の依頼フォーム**（追加する人の氏名・メールアドレス）
- **本部側の依頼一覧**と、そこから発行する導線
- **既存の組織に2人目を足す仕組み**

3つ目に落とし穴がある。いまは `auth.users` に行が入るたびに
`handle_new_user()` が**新しい組織を作る**（`20260803000001_auth_signup_trigger.sql`）。
そのまま2人目を作ると、同じ会社なのに別の組織ができて、案件も協力会社も見えない。
既存の組織に紐づける経路を分けて作る必要がある。

あわせて、いま何人いるか・請求がいくらになるかを両方の画面に出すこと。
**気づかないうちに人数が増えて請求が上がる**のがいちばん困る。

### 4. 年額払いの扱い

追加アカウントにも2ヶ月分引きを適用するかは未定。

## リリース時にどうするか

**基本プラン1本で出すのを勧める。**

- ログイン追加は**引き合いが出てから**作る（依頼フォーム・本部側の一覧・
  既存組織への追加が要る）。それまでは電話やメールで受けて、本部が手で発行すればよい
- 営業AIの500通は、営業AI側の業種・企業がまだ揃っていないので
  そもそも使えない。**枠だけ約束して後から用意するのは危ない**

営業AIの準備ができるまでは、**月40,000円・ログイン1つ・営業AI無し**で売り、
営業AIが使えるようになった時点で500通込みに切り替えるのが素直。
その場合、先に契約した顧客の扱い（値上げしないか）を先に決めておくこと。
