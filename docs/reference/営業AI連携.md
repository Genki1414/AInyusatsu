# 営業AI連携（協力会社の開拓）

協力会社がいない業種を、**営業AI（[Genki1414/eigyouAI](https://github.com/Genki1414/eigyouAI)）に
登録されている企業**から探すための連携。

**2製品にまたがる取り決め（役割分担・API・足りないもの）は
`docs/reference/営業AI連携_設計.md`。** この文書は運用の手順。

## 誰がやるか

**AI入札部の契約者は営業AIにも登録する**（ユーザー決定 2026-08-28）。
本部が営業AIのテナントを作り、そのAPIキーをAI入札部に設定する。
**顧客は営業AIの画面を開かない。** 基本プランに送信500通/月が含まれる
（`docs/reference/価格.md`）。

接続設定は組織ごとに持ち、**本部だけが書き換えられる**（`sales_ai_connections`）。

## 送信は人がボタンを押したときだけ

CLAUDE.md「やらないこと：**問い合わせフォームへの無人の自動送信**」。
定期実行やジョブから送信を呼ばない。

| やる | やらない |
|---|---|
| 何社いるかを見る（`preview`） | 無人での送信 |
| 送信先リストを作る（`lists`） | 送信の予約 |
| 打診文を組み立てる | 相手ごとの文面の作り分け（営業AI側の役目） |
| **ボタンが押されたら送信を頼む（`send`）** | 送信の再試行の自動化 |

**安全装置は営業AI側にある。** 送信先の除外（`suppression` / `tenant_exclusions`）、
回数の上限、停止スイッチは営業AIの `send_campaign()` が持っている。
こちらで作り直すと二重になり、片方だけ直したときに食い違う。

## 設定（本部の `/admin/accounts`）

アカウント一覧の各行にある「営業AI連携」を開く。

| 項目 | 内容 |
|---|---|
| 営業AIのURL | `https://...`。**http は通さない**（APIキーを平文で送らないため） |
| APIキー | 営業AIのテナントAPIキー。保存後は伏せ字でしか表示しない |
| 業種の対応表 | 1行1件「`電気 = denki`」 |

「つながるか確認する」で、件数を見るだけの問い合わせを1回送る。
失敗したら理由を `check_error` に残し、次に開いたときにも見えるようにする。

### 開かなくても状態が分かるようにしてある

行の見出しに状態が出る（`packages/domain/src/sales_ai.ts` の `salesAiSetupState`）。

| 表示 | 意味 |
|---|---|
| 未設定 | URLかAPIキーが入っていない |
| 対応表が空 | 保存はされているが、どの業種でもボタンが出ない |
| 未確認 | 保存したが「つながるか確認する」をまだ押していない |
| 確認に失敗 | 前回の確認が失敗したまま |
| 設定済み | 揃っている |

**「対応表が空」と「未設定」は、顧客からは同じに見える**（案件画面にボタンが出ない）。
本部側で区別できるようにしてある。

### 顧客の画面には入力欄が無い

顧客の「自社情報」には、使えるかどうかと対応している業種名だけが出る。
増やしたいときは本部へ連絡してもらう。

### APIキーは顧客のRLSでも読めない

`api_key` は `authenticated` から**列の読み取り権限を外してある**
（`20260828000002_sales_ai_connections_admin.sql`）。
キーを取り出せると営業AIのAPIを直に叩けてしまい、
「件数を見てから送る」「対応表に無い業種では送らない」という歯止めが全部外れるため。

キーが要る処理（案件画面の候補検索・送信）はサーバー側で `service_role` で読む
（`apps/web/lib/sales-ai.ts`）。

## 業種の対応表がなぜ要るか

AI入札部の業種（電気・清掃・警備…）と営業AI側の業種コードは**別の語彙**で、
**営業AIには語彙を返すAPIが無い**。こちらからは知りようがないので、本部が手で書く。

### 対応が無い業種では動かさない

営業AIの絞り込み（`target_lists.build_filter_sql`）は、**知らない業種の値を黙って捨てる**。

```python
trades = [t for t in trades if t in _ALLOWED_TRADES]   # 知らない値は消える
if trades:                                             # 空なら条件そのものが付かない
    clauses.append(...)
```

捨てられると業種の条件が消えて、**その都道府県の全社が対象になる**。
面識の無い会社への一斉送信になるので、次の3か所で止めている。

1. 画面：対応表に無い業種ではボタンを出さない（本部が設定した対応表を見る）
2. サーバー：変換できなければ呼びに行かず理由を返す（`outreach-actions.ts`）
3. アダプタ：`trades` が空なら `fetch` する前に止める（`eigyou_ai.ts`）

## 使う流れ

1. 案件の「見積依頼」タブを開く
2. 依頼先が0社の業種に「営業AIで候補を探して送る」が出る
3. **何社いるか見る** → 件数と数社の名前が出る
4. **◯社へ送信する** → 確認ダイアログ → リスト作成と送信が続けて走る

**利用者がやるのは4のボタンを押すことだけ。** 件数を見ずには送れないようにしてある
（何社に送るか知らないまま押させない）。送信は取り消せないので確認を挟む。

リストを作れたが送信で失敗した場合は、リストの番号を画面に残す。
作り直すと同じ会社に二重で送ることになるため。

### 1回では全部送れない

営業AIは1回の呼び出しで最大50社まで（`FORM_MAX_PER_RUN`）、
1テナント1時間で最大50社（`FORM_MAX_PER_TENANT_PER_HOUR`）。
超えた分は送られずに残る。

そのため「50社へ送信しました。残り70社はまだ送れていません」のように、
**送れなかった分を必ず出す**。ボタンは「続きを送信する」に変わり、
もう一度押すと送れていない会社にだけ送る（送信済みの会社には送らない）。

**送った数をごまかさない。** 送信は取り消せないので、
利用者が「全部送った」と思い込んだまま次の案件へ進むのがいちばん困る。

### 送り直しは同じリストへ積む

一度作った送信先リストの番号を `outreach_sends` に控えている。
2回目以降の「続きを送信する」は、**新しいリストを作らず同じリストへ送る**。

新しいリストを作ると営業AI側では新しいキャンペーンになり、
送信済みの判定（`touches(campaign_id, company_id)`）がやり直しになるため、
**もう送った会社にもう一度届く**。控えが読めなかったときは送信しない。

### 直近30日に送った会社は自動で外れる

送信のたびに `cancel_recent_days: 30` を渡している。

営業AIの `can_contact()` には接触の頻度・回数の制限がもう無い
（T44 で撤廃。残っているのは配信停止・テナント除外・重複のみ）。
企業データは全テナント共有なので、何もしないと同じ会社へ何度も届く。
**相手はこれから協力会社になってもらう会社**なので、そこは守る。

記録は営業AI側に一本化する。こちらに送信済みの表を持つと必ず食い違う。

履行場所から都道府県が取れれば地域で絞る。取れなければ絞らない（推測で別の県を入れない）。
問い合わせページが分かっている会社だけを対象にする（`contact_ready`）。

## 送った会社を協力会社にする

案件の「見積依頼」タブに「営業AIで打診した会社」が出る。
**依頼先が埋まったあとも出る**（1社登録したら一覧が消える、では続きを登録できない）。

```
「送った会社を見る」
  ↓
GET /api/tenant/lists/<id>?status=success  で実際に送れた会社を引く
  ↓
返信をもらった会社の「協力会社として登録」を押す
  ↓
partners に追加（社名・電話・メール・都道府県・業種・memo）
POST /api/tenant/lists/<id>/outcome で営業AI側にも返信を記録
```

### なぜ「返信のあった会社」を引かないのか

営業AIの `replied` は **人が手で立てるフラグ**で、
`POST /api/tenant/lists/<id>/outcome` からしかセットされない
（api.py の docstring に「β版。メール自動取得等はしない」と明記）。
営業AIはメールボックスを見ていないので、待っていても永遠に立たない。

**返信は打診文に書いた連絡先＝利用者自身のメールに届く。**
最初に気づくのは利用者なので、送った会社を出して選んでもらう。

登録したときに営業AI側にも `replied` を立てる。
営業AIのダッシュボードは `target_list_members.replied` を数えているので、
こちらだけで登録すると営業AI側は「1件も返信が無い」ままになる。

### 二重登録を防ぐ

`partners` に社名の一意制約は無い。二重に登録すると、
**同じ会社へ見積依頼が2通行く**（相手に嫌がられ、原価集計も狂う）。
社名で照合してから入れる。㈱・(株)・空白の違いだけは吸収し、
それ以上の「似ている」判定はしない（別の会社を同じとみなすほうが害が大きい）。

すでに登録済みの会社なら、行を増やさず業種を足す。

### メールアドレスが無い会社

登録はできるが、**見積依頼は送れない**（依頼はメールで送るため）。
一覧に「メール未取得」と出し、登録後のメッセージでも伝える。
推測でアドレスを入れない。

## いまの制約

**営業AIの登録企業は建設業許可業者（とび・土工／塗装／解体）だけ**で、
AI入札部が必要とする業種（電気・清掃・警備・情報処理・廃棄物処理など）とほとんど
重ならない。

営業AIは T54 で「ヒラケル」に改称し、全業種のB2B向けへ方針を変えたが、
**対象企業データの拡張はそのスコープ外**とされ、営業AIの `HANDOFF.md`
「5. 連絡すべき判断」に「データソースの選定は未着手」と残っている
（2026-08-28 時点でコードを確認）。

それまでは対応表に書ける行がほとんど無く、この機能はあまり動かない。
接続と安全装置を先に作ってあるので、営業AI側が揃った日につながる。

## 使っている営業AIのAPI

参照：`eigyouAI/api.py`

| 用途 | エンドポイント |
|---|---|
| 件数の確認 | `POST /api/tenant/lists/preview` |
| リストの作成 | `POST /api/tenant/lists` |
| 送信 | `POST /api/tenant/lists/<id>/send`（`dry_run: false`, `cancel_recent_days: 30`） |

認証は `Authorization: Bearer <tenant.api_key>`。

営業AI側の既定は `dry_run: true`（送らない）なので、明示的に `false` を送っている。

### 送信の応答は `stats` の中を見る

```json
{ "target_count": 120, "dry_run": false, "cancelled_recent": 4,
  "stats": { "sent": 50, "failed": 70, "blocked": 0, "suppressed": 0, "stopped": 0 } }
```

**上位に `sent` は無い。** 以前ここを読み違えていて、
実際には送信できているのに「送信できませんでした」と表示していた
（2026-08-28 修正）。`stats.failed` には送信上限に当たった分も入る。
