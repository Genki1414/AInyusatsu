# 営業AI連携（協力会社の開拓）

協力会社がいない業種を、**営業AI（[Genki1414/eigyouAI](https://github.com/Genki1414/eigyouAI)）に
登録されている企業**から探すための連携。

**2製品にまたがる取り決め（役割分担・API・足りないもの）は
`docs/reference/営業AI連携_設計.md`。** この文書は運用の手順。

## 誰がやるか

**AI入札部の契約者は営業AIにも登録する**（ユーザー決定 2026-08-28）。
本部が営業AIのテナントを作り、そのAPIキーをAI入札部に設定する。
**顧客は営業AIの画面を開かない。** 基本プランに送信500通/月が含まれる
（`docs/reference/価格.md`）。

接続設定は組織ごとに持ち、**本部だけが書き換えられる**（`sales_ai_connections`）。

## 送信は人がボタンを押したときだけ

CLAUDE.md「やらないこと：**問い合わせフォームへの無人の自動送信**」。
定期実行やジョブから送信を呼ばない。

| やる | やらない |
|---|---|
| 何社いるかを見る（`preview`） | 無人での送信 |
| 送信先リストを作る（`lists`） | 送信の予約 |
| 打診文を組み立てる | 相手ごとの文面の作り分け（営業AI側の役目） |
| **ボタンが押されたら送信を頼む（`send`）** | 送信の再試行の自動化 |

**安全装置は営業AI側にある。** 送信先の除外（`suppression` / `tenant_exclusions`）、
回数の上限、停止スイッチは営業AIの `send_campaign()` が持っている。
こちらで作り直すと二重になり、片方だけ直したときに食い違う。

## 設定（本部の `/admin/accounts`）

アカウント一覧の各行にある「営業AI連携」を開く。

| 項目 | 内容 |
|---|---|
| 営業AIのURL | `https://...`。**http は通さない**（APIキーを平文で送らないため） |
| APIキー | 営業AIのテナントAPIキー。保存後は伏せ字でしか表示しない |
| 業種の対応表 | 1行1件「`電気 = denki`」 |

「つながるか確認する」で、件数を見るだけの問い合わせを1回送る。
失敗したら理由を `check_error` に残し、次に開いたときにも見えるようにする。

### 開かなくても状態が分かるようにしてある

行の見出しに状態が出る（`packages/domain/src/sales_ai.ts` の `salesAiSetupState`）。

| 表示 | 意味 |
|---|---|
| 未設定 | URLかAPIキーが入っていない |
| 対応表が空 | 保存はされているが、どの業種でもボタンが出ない |
| 未確認 | 保存したが「つながるか確認する」をまだ押していない |
| 確認に失敗 | 前回の確認が失敗したまま |
| 設定済み | 揃っている |

**「対応表が空」と「未設定」は、顧客からは同じに見える**（案件画面にボタンが出ない）。
本部側で区別できるようにしてある。

### 顧客の画面には入力欄が無い

顧客の「自社情報」には、使えるかどうかと対応している業種名だけが出る。
増やしたいときは本部へ連絡してもらう。

### APIキーは顧客のRLSでも読めない

`api_key` は `authenticated` から**列の読み取り権限を外してある**
（`20260828000002_sales_ai_connections_admin.sql`）。
キーを取り出せると営業AIのAPIを直に叩けてしまい、
「件数を見てから送る」「対応表に無い業種では送らない」という歯止めが全部外れるため。

キーが要る処理（案件画面の候補検索・送信）はサーバー側で `service_role` で読む
（`apps/web/lib/sales-ai.ts`）。

## 業種の対応表がなぜ要るか

AI入札部の業種（電気・清掃・警備…）と営業AI側の業種コードは**別の語彙**で、
**営業AIには語彙を返すAPIが無い**。こちらからは知りようがないので、本部が手で書く。

### 対応が無い業種では動かさない

営業AIの絞り込み（`target_lists.build_filter_sql`）は、**知らない業種の値を黙って捨てる**。

```python
trades = [t for t in trades if t in _ALLOWED_TRADES]   # 知らない値は消える
if trades:                                             # 空なら条件そのものが付かない
    clauses.append(...)
```

捨てられると業種の条件が消えて、**その都道府県の全社が対象になる**。
面識の無い会社への一斉送信になるので、次の3か所で止めている。

1. 画面：対応表に無い業種ではボタンを出さない（本部が設定した対応表を見る）
2. サーバー：変換できなければ呼びに行かず理由を返す（`outreach-actions.ts`）
3. アダプタ：`trades` が空なら `fetch` する前に止める（`eigyou_ai.ts`）

## 使う流れ

1. 案件の「見積依頼」タブを開く
2. 依頼先が0社の業種に「営業AIで候補を探して送る」が出る
3. **何社いるか見る** → 件数と数社の名前が出る
4. **◯社へ送信する** → 確認ダイアログ → リスト作成と送信が続けて走る

**利用者がやるのは4のボタンを押すことだけ。** 件数を見ずには送れないようにしてある
（何社に送るか知らないまま押させない）。送信は取り消せないので確認を挟む。

リストを作れたが送信で失敗した場合は、リストの番号を画面に残す。
作り直すと同じ会社に二重で送ることになるため。

履行場所から都道府県が取れれば地域で絞る。取れなければ絞らない（推測で別の県を入れない）。
問い合わせページが分かっている会社だけを対象にする（`contact_ready`）。

## いまの制約

**営業AIの登録企業は建設業許可業者（とび・土工／塗装／解体）だけ**で、
AI入札部が必要とする業種（電気・清掃・警備・情報処理・廃棄物処理など）とほとんど
重ならない。営業AI側で業種と企業を増やす作業が進行中（2026-08-28）。

それまでは対応表に書ける行がほとんど無く、この機能はあまり動かない。
接続と安全装置を先に作ってあるので、営業AI側が揃った日につながる。

## 使っている営業AIのAPI

参照：`eigyouAI/api.py`

| 用途 | エンドポイント |
|---|---|
| 件数の確認 | `POST /api/tenant/lists/preview` |
| リストの作成 | `POST /api/tenant/lists` |
| 送信 | `POST /api/tenant/lists/<id>/send`（`dry_run: false`） |

認証は `Authorization: Bearer <tenant.api_key>`。

営業AI側の既定は `dry_run: true`（送らない）なので、明示的に `false` を送っている。
