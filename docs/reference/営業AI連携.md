# 営業AI連携（協力会社の開拓）

協力会社がいない業種を、**営業AI（[Genki1414/eigyouAI](https://github.com/Genki1414/eigyouAI)）に
登録されている企業**から探すための連携。

**2製品にまたがる取り決め（役割分担・API・足りないもの）は
`docs/reference/営業AI連携_設計.md`。** この文書は運用の手順。

## 誰がやるか

**AI入札部の契約者は営業AIにも登録する**（ユーザー決定 2026-08-28）。
本部が営業AIのテナントを作り、そのAPIキーをAI入札部に設定する。
**顧客は営業AIの画面を開かない。** 基本プランに送信500通/月が含まれる
（`docs/reference/価格.md`）。

接続設定は組織ごとに持つ（`sales_ai_connections`）。

## 送信は人がボタンを押したときだけ

CLAUDE.md「やらないこと：**問い合わせフォームへの無人の自動送信**」。
定期実行やジョブから送信を呼ばない。

| やる | やらない |
|---|---|
| 何社いるかを見る（`preview`） | 無人での送信 |
| 送信先リストを作る（`lists`） | 送信の予約 |
| 打診文を組み立てる | 相手ごとの文面の作り分け（営業AI側の役目） |
| **ボタンが押されたら送信を頼む（`send`）** | 送信の再試行の自動化 |

**安全装置は営業AI側にある。** 送信先の除外（`suppression` / `tenant_exclusions`）、
回数の上限、停止スイッチは営業AIの `send_campaign()` が持っている。
こちらで作り直すと二重になり、片方だけ直したときに食い違う。

## 設定（テナント作成は本部が `/admin/sales-ai` で行う。送信元は顧客が自分で入力する）

本部がAI入札部の契約者ごとに、営業AIのテナントを作る（`apps/web/app/admin/sales-ai`）。
**顧客側の「自社情報」画面には接続設定（URL・APIキー）を置かない**——顧客に営業AIの
APIキーを教える運用を避けるため（ユーザー決定 2026-08-28）。

| 操作（本部・`/admin/sales-ai`） | 内容 |
|---|---|
| 営業AIにテナントを作る | 会社名・送信元メールアドレスを入れて送信。営業AI側にテナントが作られ、APIキーは本部にも表示せずそのまま保存する |
| 送信元を今すぐ同期する | 下記の自動同期が失敗したときのやり直し用。入力欄は無い（本部が値を打ち直すことはない） |
| 接続を手で編集する | 営業AIのURL・APIキー・テナントID・業種の対応表（1行1件「`電気 = denki`」）を直接書き換える。既に発行済みのキーを貼るときにも使う。中の「業種コードを確認する」で、営業AI側の実際のコード一覧を表示できる（対応表への反映は引き続き手で書き写す） |
| つながるか確認する | 件数を見るだけの問い合わせを1回送る。失敗したら理由を `check_error` に残し、次に開いたときにも見える |

**送信元（協力会社開拓の問い合わせフォームに載る、契約者本人の名義）は、顧客が
自分で `/company`（自社情報）に入力する。** 最初は本部が毎回手入力していたが、
手間が多すぎるというユーザー決定（2026-08-28その2）で自動同期に変えた：
会社名・返信先は「自社情報」、姓名・フリガナ・住所・電話番号等は新設の
「郵送名義」に入力すると、保存するたびに営業AI側の送信元テンプレートへ自動反映される
（`apps/web/lib/sales_ai_sync.ts`）。本部への連絡は不要。

`sales_ai_connections.api_key`（および対応表以外の列）は顧客のRLSでも読めない
（列の読み取り権限を`authenticated`から外してある。
`supabase/migrations/20260828000002_sales_ai_connections_admin.sql`）。
顧客側の画面（`/company`）には接続設定の入力欄・編集手段は無く、
「使えるかどうか」と対応業種の表示（`SalesAiStatus`）だけを置く。
設定は本部の`/admin/sales-ai`に一本化されている。

## 業種の対応表がなぜ要るか

AI入札部の業種（電気・清掃・警備…）と営業AI側の業種コードは**別の語彙**で、
対応表（1行1件「`電気 = denki`」）に手で書く必要がある（本部側へ移したあとは本部が書く）。
営業AI側の実際のコード一覧は `GET /api/tenant/trades`（T56）で見られるようになり、
`/admin/sales-ai`の「業種コードを確認する」・`/company`の「業種コードを確認する」で
表示できる（`listTrades()`）。書き写す作業自体は残るが、当てずっぽうで書かずに済む。

### 対応が無い業種では動かさない

営業AIの絞り込み（`target_lists.build_filter_sql`）は、**知らない業種の値を黙って捨てる**。

```python
trades = [t for t in trades if t in _ALLOWED_TRADES]   # 知らない値は消える
if trades:                                             # 空なら条件そのものが付かない
    clauses.append(...)
```

捨てられると業種の条件が消えて、**その都道府県の全社が対象になる**。
面識の無い会社への一斉送信になるので、次の3か所で止めている。

1. 画面：対応表に無い業種ではボタンを出さない
2. サーバー：変換できなければ呼びに行かず理由を返す（`outreach-actions.ts`）
3. アダプタ：`trades` が空なら `fetch` する前に止める（`eigyou_ai.ts`）

## 使う流れ

1. 案件の「見積依頼」タブを開く
2. 依頼先が0社の業種に「営業AIで候補を探して送る」が出る
3. **何社いるか見る** → 件数と数社の名前が出る。同時に、営業AI側が止まっていないか・
   今月の残り送信可能数も確認する（止まっていれば警告を出し、送信ボタン自体を出さない）
4. **◯社へ送信する** → 確認ダイアログ → リスト作成と送信が続けて走る
5. 1回で全部送れないことがある（営業AIは1回50社・1時間50社の上限）。
   送れ残りがあれば **「続きを送信する」** に変わるので、もう一度押す
   （送信済みの会社には届かない）
6. 何日か経ってから、同じ場所で **「送った会社を見る」** → 実際にフォームへ
   送れた会社が一覧で出る
7. 返信をもらった会社の **「協力会社として登録」** を押す
   → `partners` に追加され、次の案件から見積依頼を出せる（営業AI側にも返信を記録する）

**利用者がやるのは4・5・7のボタンを押すことだけ。** 件数を見ずには送れないようにしてある
（何社に送るか知らないまま押させない）。送信は取り消せないので確認を挟む。

リストを作れたが送信で失敗した場合は、リストの番号を画面に残す。
作り直すと同じ会社に二重で送ることになるため。

履行場所から都道府県が取れれば地域で絞る。取れなければ絞らない（推測で別の県を入れない）。
問い合わせページが分かっている会社だけを対象にする（`contact_ready`）。

送信のたびにできる送信先リストの番号（list_id）は、案件×業種で1件だけ
`outreach_sends` に控えている。2回目以降の送信・6の「送った会社を見る」は、
どちらもこの番号を使う（新しいリストを作ると新しいキャンペーンになり、
もう送った会社にもう一度届いてしまうため）。

## いまの制約

**営業AIの登録企業は建設業許可業者（とび・土工／塗装／解体）だけ**で、
AI入札部が必要とする業種（電気・清掃・警備・情報処理・廃棄物処理など）とほとんど
重ならない。営業AI側で業種と企業を増やす作業が進行中（2026-08-28）。

それまでは対応表に書ける行がほとんど無く、この機能はあまり動かない。
接続と安全装置を先に作ってあるので、営業AI側が揃った日につながる。

## 使っている営業AIのAPI

参照：`eigyouAI/api.py`

| 用途 | エンドポイント |
|---|---|
| 件数の確認 | `POST /api/tenant/lists/preview` |
| リストの作成 | `POST /api/tenant/lists` |
| 送信 | `POST /api/tenant/lists/<id>/send`（`dry_run: false`、`cancel_recent_days: 30`） |
| 送った会社の確認（結果の取り込み） | `GET /api/tenant/lists/<id>?status=success` |
| 返信の記録 | `POST /api/tenant/lists/<id>/outcome` |
| 残り送信可能数（T55） | `GET /api/tenant/quota` |
| 停止されているかの確認 | `GET /api/tenant/kill-switch` |
| 業種コードの一覧（T56） | `GET /api/tenant/trades` |

認証は `Authorization: Bearer <tenant.api_key>`。

営業AI側の既定は `dry_run: true`（送らない）なので、明示的に `false` を送っている。
`cancel_recent_days: 30` で、直近30日に送った会社を今回の送信対象から外している
（企業データはテナント横断で共有のため）。

クォータ追加購入（500通/¥5,000単位。T55）は `POST /api/ops/tenants/<id>/quota-purchase`。
こちらはテナントの`api_key`ではなく本部専用の運用キーで呼ぶ別枠のAPIで、
決済（Stripe）はまだ繋がっていない。詳細は`docs/reference/営業AI連携_設計.md`。
