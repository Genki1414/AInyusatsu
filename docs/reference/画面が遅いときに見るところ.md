# 画面が遅いときに見るところ

「どのメニューへ行くのも3秒かかる」から調べた記録（2026-08-28）。
**推測で直そうとして2回外した**ので、見る順番を残す。

## 見る順番

1. **Vercelのログで、1回の遷移が何回のリクエストになっているか**
2. **`loading.tsx` があるか**
3. **関数とDBのリージョンが揃っているか**
4. そのうえでクエリの数

コードを読んで往復を数えるのは4番目。上の3つのほうが桁が大きい。

---

## 1. 1回の遷移が何回のリクエストになっているか

```
mcp: get_runtime_logs（group_by: requestPath）
```

実際にはこうなっていた。

```
05:53:12 GET /partners 200   ← 同じ1秒間に12回以上
05:53:12 GET /partners 200
...
```

一覧の行や絞り込みボタンが、画面に入るたびに先読みしていた。
20行あれば20回、サーバー側の描画が走る。

**繰り返し描かれるリンクには `prefetch={false}` を付ける。**
ナビゲーションのように数が少なく実際に押されるものは、付けない（先読みが効く）。

## 2. `loading.tsx` があるか

この製品の画面はすべて動的（ログイン状態で内容が変わる）。
Next.js 16 は動的な画面を **`loading.js` がある所までしか先読みしない**
（`node_modules/next/dist/docs/01-app/02-guides/prefetching.md`）。

境界が無いと、クリックしてからサーバーの描画が終わるまで**画面が固まる**。
これが「3秒なにも起きない」の正体だった。`app/loading.tsx` を1つ置けば全画面に効く。

**速くなるのではなく、待っていることが分かるようになる。** 両方要る。

## 3. リージョン

実際にこうなっていた。

| | 場所 |
|---|---|
| Vercelの関数 | `iad1`（米国東部・バージニア） |
| Supabase | `ap-northeast-1`（東京） |
| 利用者 | 日本 |

画面を1つ開くたびに太平洋を何度も往復していた。

```
ブラウザ(日本) → 関数(米国)      約150ms
関数(米国) → Supabase(東京)      約170ms × 3回
関数(米国) → ブラウザ(日本)      約150ms
                                ─────────
                                 約810ms（処理の中身と無関係）
```

`apps/web/vercel.json` で関数を東京（`hnd1`）に寄せた。

```json
{ "regions": ["hnd1"] }
```

**Vercelの Root Directory は `apps/web`** なので、`vercel.json` はリポジトリの
直下ではなくそこに置く（置く場所が違うと黙って無視される）。

確かめかた：ビルドログの1行目に `> web@0.1.0 build /vercel/path0/apps/web` と出る。

### 確かめかた

- 関数のリージョン：`get_deployment` の `regions`、またはVercelの Settings → Functions
- Supabaseのリージョン：プロジェクトのトップに出る（Settings の中ではない）

## 4. クエリの数

ここまでやってから見る。実際に直したもの：

- `requireOrgContext` が全画面で `users` → `org_access` → `organizations` を
  順番に引いていた → 埋め込みで1回に
- 案件画面が営業AIの設定を全タブで引いていた → 見積依頼タブだけに
- 案件画面のタブごとの取得が順番待ちだった → 同時に

## まだ残っているもの

`auth.getUser()` を1回の遷移で**2回**呼んでいる（proxy と画面側）。
それぞれSupabaseの認証サーバーへの往復。proxy で確認した結果を画面側へ渡せば
1回に減らせるが、**認証まわりを触る変更**になる。
リージョンを揃えれば1回あたりが数msになるので、まずそちらで足りるか見る。
