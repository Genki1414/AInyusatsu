# 運営画面（タスク4-8）

本部が使う画面。`/admin` にある。**契約・請求・収集キュー**を1枚で見る。

## 入れる人を決める

Vercelの環境変数に、運営として扱うアドレスをカンマ区切りで入れる。

```
ADMIN_EMAILS=gogo.kyuji5592@gmail.com
```

- **未設定なら誰も入れない。** 設定を忘れたときに全員が入れるより安全なため
- 権限が無いときは **404** を返す。運営画面のURLがあること自体を知らせない
- 顧客のメニューには出さない。URLを直接開く

運営かどうかを組織の役割（`users.role`）で持たせていないのは、DBに持たせると
顧客側の操作で自分を運営にできてしまう余地が生まれるため。
デプロイする人だけが変えられる場所に置いている。

## 何が見えるか

### 収集キュー（対応が必要なもの）

資料取得（`tenders.documents_failure_code`）とAI解析（`tenders.failure_code`）の
失敗を、コードごとにまとめて出す。**復旧の方法まで書く**（実装仕様書 §6）。

| コード | 何をするか |
|---|---|
| `LAYOUT_CHANGED` | **最優先。** コネクタのセレクタを直す |
| `DOC_NOT_FOUND` | 3回試して駄目なら、資料を手で登録する |
| `OCR_FAILED` | 資料を手で登録する |
| `PARSE_INVALID` | 再実行する。2回続けて失敗したら人が見る |
| `AUTH_REQUIRED` | 自動化しない。収集端末での正式取得へ回す |
| `RATE_LIMITED` | 自動で次回に回る（対応不要） |
| `OUT_OF_SCOPE` | 対応不要。登録だけしている |

**自動で直るものは件数だけ**出す。全部を一覧にすると、本当に直すべきものが埋もれる。

知らないコードが来たら、黙って捨てず**最優先で人に見せる**。

**48時間直っていない失敗**があると画面の先頭に警告が出る
（実装仕様書 §6「`LAYOUT_CHANGED` の未対応が48時間続いたら、その機関のカバレッジを
UIで『取得できていない』と明示する」）。

### 発注機関のカバレッジ

`coverage_check` と同じ判定（`packages/domain/src/coverage.ts`）。
欠測・遅延の機関を出す。**巡回未実装の機関も分母に入れる**（できていないことを隠さない）。

### 契約・請求

状態ごとの件数と、**対応が必要な契約だけ**を出す。

- お支払いが確認できていない（銀行振込なら入金を確認する）
- 解約が予約されている
- お試し期間があと7日以内で終わる

問題のない契約は出さない。入金チェックはここが入口になる。

## 注意

この画面は**組織をまたいで**読むため `service_role` を使う。
`requireAdmin()`（`apps/web/lib/admin.ts`）が運営であることを確かめたうえで
クライアントを渡している。**この関数を通さずに `service_role` を使わないこと。**

# アカウント（`/admin/accounts`）

支払いは**請求書払いのみ**（ユーザー決定 2026-08-25）。カード決済のように自動で
契約が始まらず、止まりもしないため、**誰が使えるかを本部が決める**。
セルフ登録の画面（`/signup`）は廃止した。

## 発行する

`/admin/accounts` の「アカウントを発行する」に、会社名・担当者名・メールアドレスを入れる。

- メールアドレスが**そのままログインID**になる
- 会社名は**協力会社へ送るメールの差出人名**になる（あとから顧客が「自社情報」で直せる）
- `organizations` / `users` / `company_profiles` はDBトリガー（`handle_new_user`）が作る
- 発行と同時に `org_access` が `利用中` になる

### 初期パスワード

発行すると**その場に一度だけ表示される**。DBには保存していない。
本部から本人へ、電話やメールで伝える。控え忘れたら「パスワード再発行」で作り直す。

招待メールにしていないのは、**メール送信の設定に依存させないため**。
届かないと発行そのものが止まる。

見間違えやすい文字（`0 O o` / `1 l I` / `2 Z` / `5 S` / `8 B`）は使わない。
電話で読み上げることがあるため。

## 停止する・再開する

一覧の行から行う。**停止には理由が要る**。理由は本人の画面（`/suspended`）に出る。

理由はよく使うものから選ぶ。請求書払いなので、ほとんどは未入金。

| 選べる理由 | 本人の画面での見え方 |
|---|---|
| お支払いの確認が取れていないため（既定） | ご利用を停止しています。理由：お支払いの確認が取れていないため |
| ご解約のお手続きが完了したため | 〃 |
| お客様のご依頼による一時停止のため | 〃 |
| その他（自分で書く） | 書いた文がそのまま出る |

毎回入力させると表現がぶれ、顧客に見せる文面が人によって変わるため定型にした。
文言は `packages/domain/src/org_access.ts` の `SUSPEND_REASONS`。

- 停止すると、次に画面を開いたときから顧客向けの画面がすべて使えなくなる
- ログイン自体は通る。行き先が `/suspended` になる
- 再開すると、理由は消える

止めているのは `requireOrgContext()`（`apps/web/lib/auth.ts`）1か所。
顧客向けの画面はすべてここを通るので、画面を増やしても書き忘れが起きない。

**協力会社の回答ページ（`/q/[token]`）は停止しても開く。**
協力会社に落ち度は無く、見積の途中で切ると相手に迷惑がかかるため。

## 行が無い組織は「停止」

`org_access` の既定値は `停止`で、**行が無い組織も停止として扱う**。
作り忘れで「使えてしまう」より「使えない」ほうが安全（使えないときは本部に連絡が来る）。

`organizations` に状態を持たせていないのは、`organizations` のRLSが `for all` で、
顧客が自分で `停止` を `利用中` に戻せてしまうため。`org_access` は**読み取りだけ**を
許可し、書けるのは `service_role`（本部）だけにしている。

## Supabase側でもセルフ登録を止める

画面は消したが、Supabaseの `signUp` API 自体は開いたままになっている。
Supabase Dashboard → Authentication → Sign In / Providers → Email の
**「Allow new users to sign up」を OFF** にする。

OFFにし忘れても、勝手に作られた組織は `org_access` が無い＝停止なので使えない。
ただし `auth.users` と `organizations` の行は増えるので、切っておく。

## いまできないこと

- **1社に複数のログインを作ること。** 1組織＝1ログインで運用する
- **アカウントの削除。** 使わなくなったら「停止」にする（案件の履歴を残すため）
