# 調達ポータル（GEPS）巡回 確認事項

**2026-08-01、ユーザーが実際にローカルから`pnpm --filter worker geps:crawl`を実行し、
ブラウザのソース表示で実際のDOM構造を確認しながら修正を進めています。** 以下、確認済みの
事項は随時この文書に反映していきます。

## 0. 確認できたこと（確定）

- **検索URL：`https://www.p-portal.go.jp/pps-web-biz/UAA01/OAA0101`**
  （設計時の想定`UZA01/OZA0101`は誤り。タブ表示「調達情報の検索」で実機確認済み。
  `apps/worker/connectors/geps.ts`のSEARCH_URLに反映済み）
- ログイン不要で検索・資料ダウンロードが可能
- 資料ダウンロードは「連絡先情報をはじめから入力する」でICカード不要（商号・氏名・電話・メールの4項目）。
  実際の画面の項目名（商号又は名称・氏名・電話番号・メールアドレス）も実機確認済みで一致
- 1日あたり実測123件（500件の上限に余裕あり）
- 実例（国土交通省 高田管内消融雪設備点検整備業務）で取得できた10ファイルの資料種別対応
- **公開開始日の入力欄：** `<label for="start-date-from">公開開始日の自</label>` /
  `<label for="start-date-to">公開開始日の至</label>`。設計時の想定
  （「公開開始日（開始）」「公開開始日（終了）」）は誤りで、実際は「〜の自」「〜の至」。
  `apps/worker/connectors/geps.ts`の`searchByDate`に反映済み
- **公開開始日の入力フォーマット：`YYYY/MM/DD`（スラッシュ区切り）。** カレンダーで日付を
  選択して実機確認済み（`YYYY-MM-DD`のハイフン区切りで送信すると検索結果が0件になっていた）。
  `searchByDate`で`dateIso`をスラッシュ区切りに変換してから`.fill()`するよう修正済み
- 検索ボタンは `<input type="submit" value="検索 " id="OAA0102">`。`検索`の部分一致だと
  ページ上部のグローバルナビ（「調達情報検索」「事業者検索」ボタン）と曖昧一致するため、
  `exact: true`で一意にした
- **「分類」は radio（全て／物品・役務／簡易な公共事業）の3択のみ。** 物品だけ・役務だけを
  検索フォーム側で絞り込む手段は無い。そのため検索段階では絞り込まず、案件ごとの分類は
  `extractDetailFromCurrentPage()`が詳細画面の「分類」欄から判定する。
  **修正済みの不具合：** 以前`crawl_geps.ts`は物品・役務で2回ループしていたが、検索結果自体は
  絞り込まれないため同じ日付を2回巡回するだけでなく、2回の独立したブラウザセッション間で
  機関名抽出にわずかな差異（表記ゆれ）が出ると、同じ`code`（調達案件番号）で異なる
  `dedupe_key`になり`tenders_code_key`一意制約違反で失敗することが実機で判明した
  （ユーザーの実行結果で発覚）。1日1回だけ巡回する設計に修正した
  （`runGepsCrawlForCategory`→`runDailyGepsCrawl`に統合。`crawlDate`からも`category`引数を削除）
- **「公示本文」リンクは`javascript:doSubmitParams(...)`によるページ内フォーム送信で、
  通常の`<a href="...">`ではない。** hrefを事前に取得して`page.goto()`する旧実装は
  `net::ERR_ABORTED`で失敗する（実機確認済み）。実際にリンクを`.click()`して遷移させる
  必要がある（`openDetailByIndex()`）。この遷移が本物のページ内遷移（別タブではない）である
  ため、詳細画面・資料DL画面から一覧に戻る手段（ブラウザバックが確実に効くか）も未検証
  であり、安全のため案件ごとに検索をやり直す設計にした（**1日あたりの検索回数が案件数分に
  増える＝低速化**。実測123件なら最大123回検索することになる。物品・役務2回巡回を1回に
  まとめたことで、この低速化は半分に緩和された。遅すぎる場合はブラウザバックでの復元に
  切り替える最適化を検討する）
- **修正済みの不具合：詳細画面への遷移待ちの競合。** `openDetailByIndex()`が
  `Promise.all([page.waitForLoadState("networkidle"), link.click()])`で遷移を待っていたが、
  `waitForLoadState`はクリックが引き起こす遷移そのものとは紐付いておらず、遷移が始まる前に
  resolveしてしまう競合が実機で高頻度（実測50件中31件＝6割超）発生していた（詳細画面が
  まだ読み込み中や検索結果画面のままの状態で読み取りを始め、`skipped`が異常に多くなっていた）。
  `page.waitForURL(/OAA0104/)`で詳細画面のURLへの遷移を明示的に待つよう修正した
- **詳細画面の各項目のDOM構造：`<tr><th>ラベル</th><td>値</td></tr>`という表構造（実機確認済み）。**
  以前の実装（`getByText(ラベル)`の次の兄弟要素を値とみなす）は、`getByText`が部分一致で
  ラベル文字列以外の要素にもマッチしうるため、隣の項目のラベルを誤って値として取得することが
  実機で確認された（例：「調達案件番号」の値として次の項目のラベル「調達機関」が入り、
  `tenders_code_key`一意制約違反を起こした）。`th:text-is("ラベル") + td`
  （thとの完全一致＋直後のtd兄弟要素）に変更して修正した。「公告内容」の外部リンク判定も
  同様に`th:text-is("公告内容") + td a`に変更した
- **「調達資料 ダウンロードURL」の実際の文言・構造：** 想定（「調達資料 ダウンロードURL」・
  半角スペース区切り・単一）と異なり、実際は「**調達資料１ダウンロードURL**」（間に空白
  無し、全角数字）で、**資料は「調達資料1」〜「調達資料5」まで番号ごとに個別のリンクに
  なりうる**（無ければ「-」表示）。hrefは通常のURL（`geps.go.jp/biz-contract/...`）で
  javascript:リンクではなかった（`page.goto()`で正しく遷移できる）。
  **修正済みの不具合：** 番号は全角数字（１２３…）だが、正規表現の`\d`は半角数字にしか
  マッチしないため、`/^調達資料\d+ダウンロードURL/`では実機で1件もヒットせず
  `documents`が常に0になっていた。全角数字（０-９）も含めた
  `/^調達資料[0-9０-９]+ダウンロードURL/`に修正した。
  **現状の制約：** 番号が最小の1件だけを取得する実装にしている。複数資料をすべて取得する
  対応は未実装（§2参照）
- **連絡先情報入力方法選択画面の実際の構造：** リンクやボタンではなく**radio**（「電子調達
  システムに登録している連絡先情報を利用する」〈既定で選択済み〉／「連絡先情報をはじめから
  入力する」の2択）で、選択後に「次へ」ボタンを押して次の画面に進む方式だった。
  `downloadDocuments()`を、後者のradioを`.check()`してから「次へ」をクリックするよう修正した

## 3. 設計上の判断（変更点）

- **収集端末（IC）は使わない。** ユーザーの指示により、資料ダウンロードは
  「連絡先情報をはじめから入力する」経路のみを実装し、`collector_agents`・
  `fetch_documents_ic` は使わない設計にした
- **機関マスタの自動登録：** GEPSの「調達機関」は実在する発注機関名（例:「北陸地方整備局」）
  であり、KKJの都道府県/市区町村コードとは異なり、そのまま`agencies`の1行として扱える粒度。
  そのため、機関マスタに無い機関は`agencyIdFromName()`（機関名の正規化＋ハッシュ）で
  自動的に`agencies`へ登録する設計にした（`category: "発注機関"`、`sources: []`）。
  KKJでは同様の自動登録を見送ったが（`docs/reference/KKJ_API_確認事項.md` §1参照）、
  データの性質が異なるため判断も変えている
- **資格区分（qual_category）：** GEPSの検索結果・詳細画面からは確定できないため、
  推測せず `"未判定"` とする。AI解析（公告PDFのパース、タスク2-3以降）で確定させる想定
- **提出期限：** 同様に確定できないため、`submit_deadline`等はnullのままとし、
  dedupe_keyの日付部分は`"unknown"`になる（`dedupeKey()`の既定動作）
