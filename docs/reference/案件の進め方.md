# 案件の進め方（判断と段取り）

案件を開いて最初に決めるのは「やるかどうか」。決めたあとに何をするかは、
参加を決めた案件にだけ出す。

## 4つから選ぶ

| | 意味 |
|---|---|
| 検討 | やるかもしれない。まだ決めていない |
| 保留 | いまは動かない。あとで見直す |
| 参加 | 出す。段取りが出る |
| 見送り | 出さない |

初期値は**未定**（何も選んでいない）。選ばなかったことを「検討」と決めつけない。

`company_tenders.stance` に入る。**利用者が決めるものなので、機械が勝手に変えない。**

### work_status とは別の軸

`work_status`（募集開始 / 積算中 / 提出済）は**作業がどこまで進んだか**で、
応札価格を入れた・書類を出した、といった操作で自動的に動く。

1つの列に混ぜると、価格を入れた拍子に「参加」が消えるようなことが起きる。分けてある。

### proposals.status とも別

`proposals.status` の「検討中 / 対象外」は**条件セットごとの提案**の状態で、
1つの案件が条件セットの数だけ行を持つ。同じ案件に「検討中」と「対象外」が並びうる。

利用者が決めるのは案件そのものへの態度なので、`(org_id, tender_id)` で1つに決まる
`company_tenders` に置いた。

## 参加を決めると段取りが出る

```
[✓] 資料を御社の名義で取得する               2026/09/05  あと7日   「資料」タブで「取得済」になっています
[ ] 不明点を質問する            任意         2026/09/05  あと7日
[✓] 協力会社へ見積を依頼する                 2026/09/12  あと14日  見積依頼を送った記録があります
[ ] 見積を集めて応札価格を決める  いま        2026/09/12  あと14日  ［この作業へ］
[ ] 提出書類をそろえる                       2026/09/12  あと14日
[ ] 入札書を提出する                         2026/09/12  あと14日
[ ] 開札                                     2026/09/15  あと17日
```

判定は `packages/domain/src/tender_stance.ts` の `buildRoadmap()`。

- **「いま」は1つだけ。** 全部に印を付けると、どれから手を付けるか分からない
- **済んだ段取りも消さない。** 消すと何をやったか分からなくなる。印を変えて残す
- **日付と残り日数を必ず並べる**（ユーザー要望 2026-08-31）。
  「あと2日」だけでは、いつが締切かを自分で数えることになる。
  日付だけでは、急ぎかどうかが一目で分からない
- **期限が取れていない段取りは日付を出さない**（「期限は未確認」）。
  推測した日付を段取りに載せると、それに合わせて動いてしまう（CLAUDE.md 最重要の前提5）
- 3日以内は赤で出す。**期限が取れていないものは赤くしない**（分からないものを急かさない）
- 「いま」の行から、その作業のタブへ直接飛べる（探させない）

### やったことは自分でチェックできる（ユーザー要望 2026-08-31）

段取りの左のチェックを押すと、やったことを記録できる。
`company_tenders.roadmap_done` にキー（`docs` / `qa` / `quote` / `price` / `forms` / `submit` / `open`）で入る。

**画面の文言とは別にキーで持つ。** ラベルを直しても、記録が消えないようにするため。

#### 押した瞬間に印を付ける（ユーザー報告 2026-08-31）

サーバーの返事を待つと3秒ほど何も起きず、押せていないと思って押し直されていた。
`useOptimistic` で先に印を付け、保存は裏で待つ。失敗したら印が戻り、理由が出る。

- **印と「いま」を同時に動かす。** チェックだけ付いて「いま」が前の行に残ると、
  どちらが本当か分からない。両方を同じ材料から出す
- **日付と残り日数は数え直さない。** サーバーが出したものをそのまま使う。
  画面側で計算し直すと、日付が変わる時刻をまたいだときに server と client で違う数字になる

#### 本サービスが知っている段取りは、外させない

| キー | 本サービスの記録 |
|---|---|
| docs | 「資料」タブが「取得済」 |
| quote | 見積依頼を送った |
| price | 応札価格を決めた |
| forms | 提出書類がすべて「用意できた」 |
| submit | 「提出済」になっている |
| qa | **分からない**（電話でも聞けるため） |
| open | **分からない**（機関ごとに公表の形が違う） |

記録で終わったと分かる段取りは、チェック済みのまま押せなくしてある。
画面が記録に反することを書くと、どちらが本当か分からなくなる。
**なぜ押せないかは、その場に文で出す**（黙って効かないチェックにしない）。

`qa` と `open` は本サービスには届かない。**取れないものを取れたことにしない**
（CLAUDE.md 最重要の前提7）ので、ここは人が入れる。

手でチェックを足すのは、どの段取りにもできる（本部の記録より先に自分で進めることがある）。
外せるのは、記録が無いものだけ。

### 質問は任意（やらなくても先へ進める）

質問はしないで進むことがある。**終わっていなくても「いま」にしない。**
ここで止めると、質問しない案件がいつまでも先へ進まない。

以前は「資料が取れていれば質問も済」としていたが、
これは**聞いていないことを聞いたことにしていた**ので、やめた。
いまは「任意」と出したうえで、聞いたなら自分でチェックしてもらう。

## 一覧から探す

「すべての案件」の絞り込みに「判断」がある。**参加・検討・保留・見送り**で絞れる。

**「未定」は選べない。** まだ何も決めていない案件は `company_tenders` に行が無く、
内部結合で落ちるため。出せない選択肢は置かない。

## 判断は一覧にも出す（ユーザー決定 2026-08-29）

案件ページを開かないと自分の判断が分からないと、同じ案件を何度も開き直すことになる。
「すべての案件」の各行に、決めた判断を出す。

- **「未定」は出さない。** まだ決めていないものに印を付けると、決めたように見える
- 入札の結果が入っていれば「結果：落札」のように並べて出す（未入力は出さない）

## 提出期限が切れた案件は既定で出さない（ユーザー決定 2026-08-29）

出しても参加できないので、一覧を埋めるだけになる。
**絞り込みをかけているときだけ出す**（過去の案件を探すことはあるため）。

2つ、消さないものがある。

- **提出期限が取れていない案件**は消さない。「期限が無い」と「期限が過ぎた」は別
  （CLAUDE.md 最重要の前提5）。取れていないことを理由に隠すと、案件そのものが消える
- **参加を決めた案件**は、期限が過ぎても一覧の先頭の「参加中の案件」に残す。
  結果を記録するまでが1件だから。過ぎたことは「提出期限を過ぎています」と添えて隠さない

## 入札の結果を記録する（ユーザー決定 2026-08-29）

参加を決めた案件の段取りの下に、開札のあとで結果を入れる欄が出る。

| 結果 | 金額欄 |
|---|---|
| 落札 | 落札金額（御社） |
| 落札できず | 落札金額（他社。分かれば） |
| 辞退 | 出さない |
| 中止 | 出さない |

- **なぜ人が入れるか。** 開札の結果は発注機関が公表するが、形も時期も機関ごとにばらばらで
  自動では拾えない。落札実績オープンデータ（awards）は月次で、案件との突き合わせも
  名称頼りなので「この案件で自社が落札したか」は分からない。
  **取れないものを取れたことにしない**（CLAUDE.md 最重要の前提7）
- **結果は stance を上書きしない。** stance は入札の前に決める意思、結果は後から分かる事実。
  同じ列にすると、そもそも参加したのかが分からなくなる。「参加」のまま「落札」を持たせる
- **辞退・中止では金額を持たせない。** 決まった金額が無いのに数字が残ると、
  あとで相場の材料として読み違える
- **開札の日より前には欄を出さない**（まだ分からないものを入れさせない）。
  開札日が取れていなければ提出期限で代え、どちらも取れていなければいつでも入れられる

金額は円単位の integer（`company_tenders.result_amount`）。カンマと全角の数字も受ける。

### 落札した案件を見る

一覧の絞り込みに「結果」がある。**結果：落札**で絞ると落札できた案件だけが並ぶ。
提出期限が切れていても、絞り込み中なので出る。

## 残り日数の数え方（2026-08-31 に1本化）

同じ提出期限に対して、画面ごとに違う日数が出ていた。
案件ページの見出しは「2026/09/02（残3日）」、同じ画面の段取りは「あと2日」。

原因は、見出し側が**経過ミリ秒を切り上げていた**こと。
締切が 9/2 17:00 なら、8/31 の朝に見れば 2日9時間 → 切り上げて3日、
同じ日の夜に見れば 1日19時間 → 切り上げて2日。**見る時刻で数字が変わっていた。**
しかも実際に残っている日は 9/1 と 9/2 の2日だけなので、「残3日」は多く見せていた。

期限の誤りは失格に直結する（CLAUDE.md 最重要の前提5）。
数え方を `packages/domain/src/deadline.ts` に1本化した。

- **日本時間の「日付の差」で数える。** 今日が期限なら0、明日なら1。
  その日のあいだは何時に見ても同じ数字になる
- **時刻は捨てる。** 締切が 9/2 17:00 でも 9/2 09:00 でも「9/2 が締切」であることは変わらない。
  何時までかは公告の原本で確かめてもらう（画面の数字で締切時刻を判断させない）
- 期限が取れていなければ null。**0や大きい数を返さない**

使っているところ：案件ページの見出し（`due()`）、段取り、すべての案件、
提案された案件、今日やること、参加判断の点数（`fit.ts` の残日数10点）。
