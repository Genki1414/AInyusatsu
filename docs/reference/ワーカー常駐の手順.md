# ワーカー常駐の手順（Railway）

収集・解析・提案・催促を、毎日決まった時刻に自動で走らせるための設定。
これを行うまでは、すべて手でコマンドを叩く必要がある。

参照：`docs/本番環境_推奨構成.md`（収集ワーカーは Railway に Node + Playwright を常駐）

---

## 1. Postgres の接続文字列を取る

pg-boss は Supabase の REST API ではなく、Postgres へ直接つなぐ。

1. Supabase → Project Settings → Database → Connection string
2. **Session pooler** を選ぶ
3. `[YOUR-PASSWORD]` を実際のDBパスワードに置き換える

**Transaction pooler（ポート6543）は使えない。** pg-boss はセッションをまたぐ機能
（advisory lock など）を使うため、トランザクションモードのプーラーでは動かない。

## 2. Railway にサービスを作る

Railway で New Project → Deploy from GitHub repo → `Genki1414/AInyusatsu`

**ビルドの設定は要らない。** リポジトリのルートに `Dockerfile` と `railway.json` が
あるので、Railwayはそれを使う。Settings のコマンド欄は**すべて空のまま**にする。

### なぜDockerfileにしたか

Railwayの自動判定（railpack）はこのpnpmモノレポを読めず、ビルドの手前で止まる
（2026-08-31 実機で確認）。判定に頼らず、動かし方をリポジトリに固定した。

Playwright は公式イメージ（`mcr.microsoft.com/playwright:v1.62.1-noble`）を使う。
ブラウザ本体とシステムライブラリが入っているので `playwright install` が要らない。
自前で入れると、ライブラリ不足で**ビルドは通って巡回だけが実行時に落ちる**。

**playwright を上げたら、Dockerfileのタグも必ず一緒に上げること。**
ずれると「ブラウザが見つからない」で巡回だけが止まる。

## 3. 環境変数を入れる

`apps/worker/.env.example` と同じものを Railway の Variables に入れる。
最低限これだけは必須。

```
DATABASE_URL=（手順1で取ったSession poolerの接続文字列）
NEXT_PUBLIC_SUPABASE_URL=
SUPABASE_SERVICE_ROLE_KEY=
ANTHROPIC_API_KEY=
RESEND_API_KEY=
RESEND_FROM_ADDRESS=
# 本部への異常通知の宛先（カンマ区切り）。Webの運営画面と同じ値にする。
# 未設定だと異常が誰にも届かない（notify-ops がログにだけ残して終わる）
ADMIN_EMAILS=
INBOUND_EMAIL_DOMAIN=
APP_URL=
GEPS_CONTACT_COMPANY=
GEPS_CONTACT_NAME=
GEPS_CONTACT_TEL=
GEPS_CONTACT_EMAIL=
TENDER_DOCUMENTS_BUCKET=tender-documents
```

## 4. 最初は解析を止めて起動する

いきなり全部を動かさず、巡回と抽出が想定どおり動くのを見てから解析を入れる。
AI解析は実測で約69円/件なので、設定を間違えたまま回すと請求に出る。

```
DISABLED_JOBS=analyze-pending
```

ログで巡回とテキスト抽出が正常に終わることを確認したら、この行を消して再デプロイする。

**リリースまで解析を行わない場合も、この行を入れたままにする**（ユーザー判断 2026-08-22）。
巡回・抽出は費用がかからないので動かしたままでよく、解析だけを止めておける。

### 解析待ちが積み上がることを知っておく

提出期限（`submit_deadline`）はコネクタからは取れず、AI解析で初めて埋まる。
つまり**解析前の案件は提出期限が null** で、`tender-lifecycle` は終了に落とせない。
解析を止めている間、解析待ちは減らずに積み上がり続ける。

いざ解析するときに、とっくに締め切られた案件にも費用がかかるので、
そのときは公告日で絞る（次項）。

## 5. 解析の件数上限を決める

```
ANALYZE_DAILY_LIMIT=50
```

1回の実行で処理する案件数。既定は50件（約3,500円）。1日2回走るので、
既定のままなら1日あたり最大100件・約7,000円。
上限に達した分は次回に回るだけで失われない。ログに「次回へN件」と出る。

全件を処理したい場合は引き上げる。止めたいときは `0`。

### 公告日で対象を絞る（任意）

```
ANALYZE_MAX_NOTICE_AGE_DAYS=90
```

公告日がこの日数より古い案件を解析しない。長く解析を止めていた後に流すときは、
これを入れないと締め切り済みの案件にも費用がかかる。

公告日は提出期限そのものではないため、**既定では絞らない**（推測で対象を減らさない）。
絞らずに実行した場合は、その旨がログに出る。

対象がどれだけ減るかは、実行前にSQLで確かめられる。

```sql
select
  count(distinct t.id) filter (where t.notice_date >= current_date - 90) as 公告90日以内,
  count(distinct t.id) as 解析待ち合計
from tenders t
join tender_documents d on d.tender_id = t.id
where t.collect_status = '取得済' and d.extracted_text is not null;
```

## 動作の確認

起動直後のログに、登録されたジョブが一覧で出る。

```
[worker] pg-boss を起動しました
[worker] 停止中のジョブ: analyze-pending
[worker] 登録: kkj-sync  0 4,12 * * *（Asia/Tokyo）  官公需情報ポータルAPIで新規案件を検知する
...
[worker] スケジュールを解除しました: analyze-pending
[worker] 12件のジョブを登録しました。待機します
```

ここまで出れば常駐している。あとは時刻になれば自動で走る。

確認するのは3つ。

- **`pg-boss を起動しました`** — `DATABASE_URL` が正しく、Session pooler で繋がっている
- **登録が12件** — 少なければどれかが弾かれている
- **`停止中のジョブ: analyze-pending`** — `DISABLED_JOBS` が効いている

`DISABLED_JOBS` を外せば13件になる。

### 実行の時刻（Asia/Tokyo）

| 時刻 | ジョブ |
|---|---|
| 毎時 00分 | remind-quotes |
| 毎時 20分 | notify-instant |
| 0:30 / 10:30 / 18:30 | tender-lifecycle |
| 4:00 / 12:00 | kkj-sync |
| 4:30 / 12:30 | crawl-geps |
| 6:00 | coverage-check |
| 6:20 | notify-ops |
| 7:00 | notify-digest |
| 8:00 / 16:00 | extract-text |
| 11:00 / 19:00 | match-tenders |
| 毎月1日 3:00 / 3:30 | import-awards / refresh-market-rates |

**収集の結果が画面に出るのは翌朝**になる。4時に収集、4時半に資料取得、8時に抽出、11時に提案なので、
夜に設定した場合はその日のうちには何も増えない。

手元で試すこともできる（`.env.local` を読む）。

```
pnpm --filter worker start:local
```

## 止め方

- **ジョブ単位**：`DISABLED_JOBS` に名前を足して再デプロイ
- **全体**：Railway のサービスを停止する

スケジュールは Supabase の Postgres に保存されるので、ワーカーを再起動しても消えない。
`DISABLED_JOBS` で止めたジョブは、起動時にスケジュール自体も解除される。
