# Claude Code 実装指示書

この文書は、Claude Code に渡す前提で書いています。**リポジトリの `docs/` に置き、`CLAUDE.md` から参照させてください。**
仕様の詳細は `実装仕様書_v1.md`（DDL・コネクタIF・AI解析スキーマ）を正とします。

---

## 0. 進め方の原則

1. **1タスク＝1PR。** まとめて作らせない。レビューできない量になると、8月に間に合わなくなります
2. **DDLを先に確定させる。** 画面から作ると必ず作り直しになります
3. **domain（純ロジック）にはテストを必ず書く。** 適合判定と原価集計が壊れると、気づかないまま誤った提案が出ます
4. **外部サービス（Stripe・Claude API・LINE）は必ずアダプタ層で包む。** 直接呼ばない。譲渡時の差し替えと、テストのために必要です

## 2. CLAUDE.md（このまま置いてください）

```markdown
# AI入札部

全省庁統一資格で参加できる入札案件を収集・解析し、企業ごとに提案して、
協力会社への見積依頼から提出書類の準備までを支援するサービス。

## 最重要の前提

1. 案件は全ユーザー共通の1レコード（tenders）。企業ごとのデータは必ず別テーブル（proposals / company_tenders）
2. 本部が必ず資料を取得する（docs/資料取得方針_v3.md）。ICカードが必要な取得は社内の収集端末で実行する。顧客は顧客ごとに自分の名義で正式取得する（代行しない）
3. AIの抽出結果には必ず原文の引用と出典を持たせる。出典のない抽出はUIで「未確認」として扱う
4. 本部が取得した資料の原本はユーザーに配らない（解析結果と引用、公告元URLのみ提供）
5. 期限（提出・質問・開札）の誤りは失格に直結する。ここだけは推測せず、取れなければ null にする
6. 資料は公告・入札説明書・仕様書・数量表・様式の5種類すべてを取得し、すべてAI解析にかける。KKJ APIの公告本文は補助であって資料の代替ではない
7. 資料は揃わなくても、提案できる内容があれば提案する。判定できない項目は推測せず「未判定」と表示する。資料が無い理由は「機関が出していない（正常）」と「取得失敗（要対応）」を必ず分けて記録する

## 技術

- Next.js App Router / TypeScript / Tailwind
- Supabase（Postgres + Auth + Storage）。全テーブルRLS有効
- ワーカーは Railway 常駐。ジョブキューは pg-boss
- 決済は Stripe。AI は Claude API

## コードの決まり

- 外部サービスは `packages/*/adapters` 経由でのみ呼ぶ
- 純ロジックは `packages/domain` に置き、副作用を持たせない。テストを必ず書く
- DBアクセスはサーバー側のみ。service_role キーをクライアントに渡さない
- 入力は Zod で検証する
- エラーは握りつぶさない。失敗理由をコード（AUTH_REQUIRED / LAYOUT_CHANGED / OCR_FAILED / PARSE_INVALID / RATE_LIMITED / OUT_OF_SCOPE）で記録する
- 日時は DB に timestamptz、表示は Asia/Tokyo
- 金額は円単位の integer。小数を使わない

## やらないこと

- AI積算、入札書の作成、契約書の作成
- 自治体・建設工事（V2）
- 資料原本のユーザーへの配布
- 問い合わせフォームへの自動送信

## 作業の進め方

- 1タスク1PR。PRの説明に「何を満たしたら完了か」を書く
- DDLの変更は必ず migrations に追加（既存ファイルを書き換えない）
- 画面を作るときは docs/ のプロトタイプの文言をそのまま使う（表現を変えない）
```

## 5. 実装上の注意（つまずきやすい順）

1. **RLS を後回しにしない。** テーブルを作った直後にポリシーを書く。後から入れると必ず漏れます
2. **`tenders` は全 org 読み取り可・service_role のみ書き込み可。** ここだけ他と違うので明示的にコメントを残す
3. **Stripe Webhook は `stripe_event_id` で冪等に。** 同じイベントが複数回来ます
4. **ワーカーとWebアプリで Supabase クライアントを分ける。** ワーカーは service_role、Webはユーザーセッション
5. **LLM の出力は必ず Zod でパースしてから保存。** 失敗したら再実行し、2回失敗したら人へ回す
6. **PDFはメモリに載せきらない。** ストリームで Storage に流す
7. **クロールは同一ドメイン1並列・2秒間隔。** 相手のサイトに負荷をかけない。これは規約でなくマナーの問題であり、ブロックされると事業が止まります
8. **タイムゾーン。** 「2026/08/07 15:00」は JST。UTC で保存し、表示で戻す

## 6. テスト

| 対象 | 方法 |
|---|---|
| `packages/domain` | 単体テスト必須。適合判定は境界値（等級ちょうど、残日数ちょうど）を必ず入れる |
| コネクタ | **取得したHTMLをファイルに保存し、それに対するテスト**（ゴールデンテスト）。サイトが変わったら落ちる |
| AI解析 | ゴールドセット20件。CIではなく手動で実行 |
| 課金 | Stripe のテストモードで、成功・失敗・解約を通す |
| E2E | 1本だけ：登録 → 条件設定 → 提案 → 見積依頼 → 回答 → 原価集計 → 提出済み |

**E2Eを1本通すことが、8月の完了条件です。**

```
docs/実装仕様書_v1.md と CLAUDE.md を読んでから作業してください。

制約：
- 新しい依存パッケージを足す場合は理由を書く
- DDLの変更が必要なら migrations に追加し、既存ファイルは触らない
- 実装後、テストと動作確認の手順を PR の説明に書く
```

**「いい感じにやって」と言わない。** 完了の定義を必ず書きます。ここが曖昧だと、動くけれど仕様と違うものが出てきます。
